# search-rl-env

Проект открытой RL-среды для обучения агента **Text-to-SQL + RAG**. Агент отвечает на вопросы по структурированным таблицам и текстовым документам: формирует SQL-запросы, ищет сведения в корпусе и объединяет результаты. Среда предоставляет инструменты, траектории и оценку.

На собственном агенте сравним исходное качество, оптимизацию промпта через **GEPA**, **SFT-дистилляцию** от API-учителя и **RL** в среде. Рост метрики проверяется на отложенных вопросах, которые не использовались для подбора промпта или обучения модели.

## Текущее состояние

Целевая гибридная постановка описана в [AGENT_SCOPE.md](docs/AGENT_SCOPE.md). Реализованы retrieval-прототип и связанный синтетический пример SQL + RAG с ответом списком id; реальную SQL-базу и общий формат содержательного ответа ещё предстоит подключить.

Харнесс работает на **Verifiers 0.4.0, API `verifiers.v1`**: `Taskset` загружает задачи, `Task` задаёт инструменты и награду, `Harness` выполняет локальный цикл через interception Verifiers без отдельного процесса на эпизод. Публичная функция `run_episode(task, model, search, config)` сохранена. Есть моки, настраиваемый Chat Completions API, OpenRouter, терминальный прогресс и JSON с нативной `Trace`. Для размеченных задач считается Recall@10; без эталонов награда равна `null`. Проверки работают без внешних API, весов и GPU; инструменты по умолчанию вызываются в том же процессе, MCP сохранён как отдельный режим. Обновление весов и MLflow ещё не подключены. Для настоящего поиска добавлен отдельный Go-сервис с SQLite FTS5 и HTTP-клиентом на Python; стандартные демо пока используют мок.

Для подключения команды начните с [передачи харнесса](docs/HARNESS_HANDOFF.md): установка, примеры RAG/SQL/hybrid, свой пакет задач, конфиги, результаты и границы ответственности. Текущий поиск и замена мока описаны в [RAG_SEARCH.md](docs/RAG_SEARCH.md).

Для разработки используем Qwen через настраиваемый Chat Completions API. Model id задаётся явно в CLI или `MODEL_ID`; для прямого OpenRouter есть отдельный режим и `OPENROUTER_MODEL`. Пример RL-обучения затем подключается к весам модели в тренировочном окружении.

| Участник | Ответственность | Планируемые модули |
|---|---|---|
| **Сергей** | Агент, харнесс и модели: цикл действий, промпты, контекст, клиенты моделей, GEPA, SFT и RL | `agent/`, `training/` |

| **Коля** | Инфраструктура снятия бенчмарков поверх харнесса и поиска: конфиги прогонов, возобновление, метрики, затраты и отчёты | `evaluation/` |

После передачи харнесса v0 **Коля с Димой подключают бенчмарки и снимают baseline/скорость; Сергей с Вовой параллельно готовят данные GEPA/SFT**. Сергей остаётся владельцем харнесса и обучения. Runner Коли запускает агента через SQL/search Димы, вызывает оценщики Вовы и сохраняет метрики и расходы. Подробности — в [TASKS.md](docs/TASKS.md).

## Структура репозитория

Реализованы `contracts/`, `agent/`, `environment/`, Python-клиент `search/` и Go-сервис `services/search/`, примеры и тесты. Остальные компоненты ниже остаются планом:

```text
src/search_rl_env/
├── contracts/      # типы задачи, поиска, конфигурации и результата

├── environment/    # Taskset, Task, MCP-инструменты, состояние и Recall@10
├── training/       # план: обучение
├── search/         # HTTP-клиент Go-сервиса поиска
├── benchmarks/     # план: задачи, метрики и джаджи
└── evaluation/     # план: прогоны и отчёты
examples/run_episode.py # запуск одного вопроса
examples/fixtures/  # синтетический вопрос и подставная выдача без эталонов
tests/unit/agent/   # цикл, HTTP-протокол и пример запуска
docs/              # спецификации, решения и план
```

Полное дерево, владельцы и правила размещения данных — в [STRUCTURE.md](docs/STRUCTURE.md). Общие интерфейсы согласуются по примерам из [CONTRACTS.md](docs/CONTRACTS.md).

## Как начать

```bash
git clone https://github.com/SergeyBarshin/search-rl-env.git
cd search-rl-env
```

Прочитайте [правила работы](CONTRIBUTING.md), свою задачу в [TASKS.md](docs/TASKS.md) и затронутые контракты. До разработки создайте issue с результатом и способом проверки, затем рабочую ветку. Изменения вливаются в `main` через PR с ревью.

Нужен Python 3.11+. Установка из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
```

Если используете uv: `uv venv .venv`, затем `uv pip install -e '.[dev]'` и `source .venv/bin/activate`.

Бесплатный эпизод на моках:

```bash
python examples/run_episode.py --output runs/demo/episode.json
```

Ожидаемый результат: `stop_reason=finished`, документы `doc-001`, `doc-002` и JSON в указанном файле. Мок выбирает все показанные документы; это проверка взаимодействия, а не качества отбора. `runs/` исключён из Git. CLI возвращает код `0` при `finished`, `1` при остановке эпизода по другой причине.

Свой вопрос и подробный вывод в терминале:

```bash
python examples/run_episode.py --model mock \
  --question 'Какие документы описывают перенос срока проекта?' --verbose
```

`--question` заменяет вопрос в `--task`, сохраняя корпус и его ревизию. `--verbose` показывает отправку запросов, вызовы `search`/`finish` и ответы инструментов по ходу эпизода; каждые 5 секунд ожидания печатается статус, в конце — usage. Поиск возвращает фиксированную выдачу из `--hits`, поэтому для проверки результата используйте вопросы по этому синтетическому корпусу.

`--request-timeout 30` задаёт общий таймаут одного API-запроса к модели в секундах; по умолчанию — 30. При превышении сохраняется результат с `infrastructure_error` и кодом `model_timeout`. Ctrl+C завершает CLI без traceback с кодом 130 и сохраняет частичную траекторию рядом с `--output`: например, `runs/my-episode.interrupted.json`. Usage незавершённого запроса неизвестен и сохраняется как `null`; отдельный файл сохраняет прежний полный результат.

Для разрешённого запуска настоящей модели через настроенный API:

```bash
python examples/run_episode.py --model api --model-id qwen/qwen3.5-9b \
  --question 'Какие документы описывают перенос срока проекта?' --verbose \
  --max-steps 4 --max-output-tokens 2048 --max-tokens-per-step 1024 \
  --output runs/api-demo/episode.json
```

Настройте в локальном `.env` переменные `MODEL_API_URL`, `MODEL_ID` и `MODEL_API_KEY` либо `MODEL_API_KEY_FILE`. Схема заголовка авторизации задаётся через `MODEL_AUTH_SCHEME` (по умолчанию `Bearer`). Адрес и параметры доступа задаются локально; ключ не сохраняется в результате эпизода. Поиск остаётся моковым.

Модель сама выбирает запросы, число поисков и момент `finish`. Лимита поисков и остановки после нескольких ошибок нет. `--max-steps` и `--max-output-tokens` необязательны: по умолчанию оба выключены. Один запрос ограничен `--max-tokens-per-step` (512). Verifiers проверяет суммарный токенный бюджет между ходами: последний ответ может превысить его, максимум ограничивается размером ответа. Это не точный денежный лимит. При остановке по бюджету сохраняются `truncated=true` и пустой финальный список. Размер выдачи и сниппетов задаётся инструментом, порядок действий — моделью.

Seed по умолчанию не задан: некоторые доступные провайдеры Qwen его не поддерживают. `--seed 42` включает передачу seed и требует поддерживающий его маршрут; иначе API может вернуть 404 о несовместимых параметрах. Харнесс обрабатывает несколько tool calls последовательно, без требования к поддержке `parallel_tool_calls` на стороне провайдера.

Для прямого OpenRouter сохраните `OPENROUTER_API_KEY` в локальном `.env` или переменной окружения; пустой образец — [.env.example](.env.example). `.env` загружается только в режимах API и OpenRouter, переменные окружения имеют приоритет. Пример команды **для отдельно разрешённого платного запуска**; поиск остаётся моковым:

```bash
python examples/run_episode.py --model openrouter --model-id qwen/qwen3.5-9b \
  --max-steps 6 --max-output-tokens 2048 --max-tokens-per-step 512 \
  --output runs/openrouter-demo/episode.json
```

Оба клиента следуют [протоколу tool calling OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling): передают схемы при каждом запросе и возвращают результаты через `role="tool"` с исходным `tool_call_id`. Запросы не повторяются автоматически. Поддержку параметров и доступность модели проверяет провайдер; стандартные тесты не вызывают платные endpoint.

### Локальный UI для тестирования

```bash
.venv/bin/python -m search_rl_env.ui
```

Откройте [http://127.0.0.1:8866](http://127.0.0.1:8866). В интерфейсе можно выбрать сценарий «Поиск документов» или «SQL + RAG · компенсации заказов», задать вопрос, выбрать мок или модель API, посмотреть действия и результаты инструментов, остановить эпизод и скачать JSON. По умолчанию выбран мок. В сценарии SQL + RAG доступны схема и шесть строк тестовой таблицы, SQL-выдача и финальный список заказов с документами-источниками. Поиск возвращает фиксированные документы выбранного сценария. В режиме «Модель API» используются `MODEL_API_URL`, `MODEL_ID`, ключ и схема авторизации из локального `.env`; ключ в браузер не передаётся. Реальный API вызывается только после нажатия «Запустить эпизод» в этом режиме.

UI переиспользует `RolloutRunner` и общий HTTP-пул; одиночный CLI вызывает тот же цикл через `run_episode`. События поступают через SSE, полные результаты и частичные результаты отмены сохраняются в `runs/ui/<run_id>/episode.json`. Закрытие вкладки не останавливает эпизод; для этого есть кнопка «Остановить». Завершение сервера отменяет активные эпизоды. Бюджеты шагов и суммарных токенов в дополнительных параметрах по умолчанию не заданы. История запусков после перезапуска сервера в UI не восстанавливается; JSON остаётся на диске.

Если порт занят: `python -m search_rl_env.ui --port 8867`. Другой файл настроек задаётся через `--env-file`, каталог результатов — через `--output-dir`. Сервер слушает только `127.0.0.1`. Сборка фронтенда и установка npm-пакетов не нужны.

### Моковый SQL + RAG

```bash
.venv/bin/python -u examples/run_episode.py --scenario sql_rag --model mock \
  --verbose --output runs/sql-rag/episode.json
```

Связанный пример: «Какие заказы подходят под компенсацию согласно регламенту?» Поиск возвращает регламент, `sql(query)` выполняет запрос в SQLite в памяти, `finish(answer, document_ids)` возвращает id заказов и источники. Ожидаемый ответ мока — `ORD-101`, `ORD-105`; вся траектория сохраняется. У реальной модели порядок действий и запросы свободные; сценарий `search → sql → finish` запрограммирован только у моковой модели. Поиск документов как отдельный сценарий сохраняет прежний `finish(document_ids)`.

Для модели API у той же команды замените `--model mock` на `--model api`. В UI выберите сценарий SQL + RAG и режим «Модель API». Данные остаются синтетическими, ключи читаются из `.env`. Во время разработки платных вызовов не было.

Нативный Taskset поддерживает тот же пример: `vf-eval @ configs/verifiers-eval.toml --env.taskset.scenario sql_rag --dry-run`. Для размеченных гибридных задач награда равна 1 при точном совпадении множества id ответа с приватным `reference_answer`, иначе 0. Без эталона награда отсутствует. Пример демонстрирует цикл и интерфейсы, обучение весов не запускается.

### Параллельные роллауты

```bash
.venv/bin/python -u examples/run_rollouts.py --model mock --scenario sql_rag \
  --episodes 64 --concurrency 16 --output runs/parallel
```

Команда сохраняет отдельный `EpisodeResult` с нативной Trace на каждый вопрос и `summary.json`: пропускная способность, p50/p95 времени эпизода, разбивка модели/инструментов/обвязки, причины остановки и награда. Для проверки транспорта используется один синтетический вопрос с разными task id. Это не оценка качества модели. `--no-save` отключает запись эпизодов для замера скорости; `--mock-latency-ms 30` добавляет ожидание каждого ответа мока. `--model api` использует `.env` и общий клиент модели.

В Python используйте один `async with RolloutRunner(model, search, config, sql=sql, concurrency=16)` на серию; `runner.run(task)` запускает один эпизод, `runner.iter_episodes(tasks)` выдаёт результаты по мере готовности. Допустимы обычные и асинхронные источники. Для приватных эталонов и индивидуального конфига есть `RolloutRequest`. Число workers и размер буфера ограничены параллельностью; при досрочном выходе закрывайте iterator через `contextlib.aclosing`. Поиск, SQL и модель заимствуются, их клиенты закрывает вызывающий код. Пример интеграции — в [CONTRACTS.md](docs/CONTRACTS.md).

Общие listener, клиент модели и соединения живут весь batch. Состояние, история, инструменты и награда создаются заново для каждого эпизода. По умолчанию `execution=in_process`; для проверки прежнего MCP-пути есть `--execution subprocess`. Ограничение параллельности управляет ресурсами runner, число поисков остаётся решением модели. Измерения на моках и архитектура — в [HARNESS_REPORT.md](docs/HARNESS_REPORT.md#параллельные-роллауты-и-измерения).

### Профилирование эпизодов

В UI раздел «Профиль времени» разделяет запуск среды, запросы модели, инструменты, финализацию, оценку и прочую обвязку. В каждом API-шаге раскрывается HTTP-профиль: подготовка запроса, TCP/DNS, TLS, отправка, ожидание заголовков, первый декодированный байт тела, чтение и разбор JSON. Сохраняются статусы, размеры, request ID, доступные числовые Server-Timing и признак переиспользования соединения. У мока HTTP-замеры отсутствуют.

API пока возвращает готовый JSON (`stream=false`): время первого байта **не является TTFT**. Ожидание заголовков может включать очередь и генерацию. Они различаются только если сервер сообщает собственные метрики. Первый транспортный callback включает подготовку HTTPX и возможное ожидание пула; это не отдельный точный замер пула или DNS.

Рядом с результатом UI создаёт `runs/ui/<run_id>/events.jsonl`; его можно скачать кнопкой «Лог JSONL». В журнале есть временные отметки, episode/run/request id, шаги и длительности; сырые заголовки, тела запросов и результаты инструментов в него не копируются. Полная траектория остаётся в `episode.json`. Частичные HTTP-замеры сохраняются при отмене и таймауте. Сводку текущих запусков можно получить через `GET /api/runs`.

CLI с `--verbose` показывает фазы и итоговую разбивку; JSONL записывается рядом с `--output`, путь можно задать через `--event-log`. Разбор уже сохранённого эпизода без нового инференса:

```bash
.venv/bin/python -m search_rl_env.profiling runs/demo/episode.json
```

Для старых JSON выводятся доступные суммарные замеры; деталей HTTP задним числом не появляется. В UI один AsyncClient и keep-alive пул живут между эпизодами. `run_episode` допускает независимые параллельные вызовы; runner управляет их количеством. При прямом API-запуске общий `httpx.AsyncClient` передаётся через `http_client`, его закрывает создавший runner. Изоляция состояний и HTTP-профилей при таком запуске проверена тестом.

Нативный запуск Verifiers и проверка конфигурации без инференса:

```bash
.venv/bin/vf-eval @ configs/verifiers-eval.toml --dry-run
.venv/bin/vf-eval @ configs/verifiers-train-rollout.toml --dry-run
```

Первый конфиг использует Chat Completions, второй — тренировочный клиент с renderer Qwen3.5 и vLLM `/inference/v1/generate`. Для фактического запуска нужен подготовленный сервер и разрешённый бюджет; `--dry-run` только проверяет конфиг. В обоих примерах `push=false`, результаты остаются локально. Конфиги не читают `.env` автоматически: переменные авторизации должны быть в окружении.

Набор по умолчанию синтетический, поиск — моковый. `env.taskset.tasks_path` принимает JSON со списком задач и необязательными `reference_document_ids`; эталоны не включаются в промпт. Для обучения задайте **отдельный train-файл**, `require_references=true`, а dev/test запускайте отдельно. Конфиг `verifiers-train-rollout.toml` собирает траектории с параллельностью до 16, обновление весов выполняет внешний тренер. Число повторов задачи задаётся отдельно через `--num-rollouts`; проверка конфигурации серии: `.venv/bin/vf-eval @ configs/verifiers-train-rollout.toml --num-rollouts 16 --max-concurrent 16 --dry-run`. Нативные `TrainClient`, renderer и пул инференса Verifiers сохраняют token ids, logprobs и маски; синтетический тест проверяет, что токены инструментов не обучаются. Схема и границы компонентов — в [CONTRACTS.md](docs/CONTRACTS.md), архитектура и сценарии проверки — в [HARNESS_REPORT.md](docs/HARNESS_REPORT.md).

Проверки:

```bash
python -m pytest -q
git diff --check
```

Тесты покрывают несколько поисков по решению модели, нормальное завершение, бюджеты, повторы id, неизвестные документы, исправление ошибочных действий, сбои, JSON-сохранение и воспроизведение. HTTP-вызовы OpenRouter проверяются через `httpx.MockTransport`, без сети. Точные интерфейсы для поиска Димы и runner Коли — в [CONTRACTS.md](docs/CONTRACTS.md).

## Реальный пример HyDRA: SQL и поиск

Основной интеграционный пример использует train-задачу `train_a2s_4` из
[HyDRA-Bench](https://huggingface.co/datasets/Snowflake/HyDRA-Bench), исходную
BIRD-базу hockey и 999 настоящих KILT-фрагментов. SQL возвращает `Toronto Arenas`,
поиск на той же задаче проверяется через Go BM25 и опциональный FAISS/RRF.
Подробности и ограничения — в [HYDRA_PILOT.md](docs/HYDRA_PILOT.md).

```bash
python -m pip install -e '.[dev,hydra]'
python examples/prepare_hydra.py --with-vectors
go -C services/search build -o ../../build/search-service ./cmd/search
./build/search-service build
./build/search-service serve -sql-snapshot data/hydra/hockey.sqlite -db-id hockey
```

В другом терминале:

```bash
python examples/run_hydra.py --with-vectors
```

Это воспроизведение тулов с эталонным SQL, без модели агента. Данные проверки
не передаются в поисковый индекс. Все три варианта нашли фрагменты нужной статьи
в top-10 на выбранном срезе; это не официальный score полного HyDRA и не доказательство
превосходства одного метода. Компактный ONNX-энкодер работает на CPU, платных API нет.

Корпус для Go-команды build по умолчанию — `examples/fixtures/hydra/corpus.jsonl`,
снимок — `indexes/hydra.sqlite`. Старые синтетические примеры остаются только
для unit-тестов и прежних моковых CLI/UI. Без векторов можно использовать основную
установку проекта и команды без `--with-vectors`.

Обычный поиск и чтение доступны через `examples/run_search.py`; например,
`python examples/run_search.py search --query 'Toronto Arenas'`.
Архитектура HTTP-сервиса — в [SEARCH_BACKEND.md](docs/SEARCH_BACKEND.md),
источники данных и атрибуция — в [ATTRIBUTION.md](examples/fixtures/hydra/ATTRIBUTION.md).

```bash
go -C services/search test -race ./...
go -C services/search vet ./...
python -m pytest -q
git diff --check
```

## Первый совместный результат

Проект разбит на три недельных спринта: предлагаемый календарь — 2–8 ноября: харнесс, baseline и пилот данных; 9–15 ноября: GEPA, SFT и RL; 16–22 ноября: оценка, релиз и статья. Цели и демо — в [ROADMAP.md](docs/ROADMAP.md), задачи с владельцами и зависимостями — в [BACKLOG.md](docs/BACKLOG.md). GitHub Issues по плану ещё не созданы.

1. **Передача v0:** Сергей передаёт Коле интерфейс, пакетный запуск, примеры SQL/RAG/hybrid и формат траектории; Дима готовит реальные источники, Вова — оценщики.
2. **Бенчмарки:** Коля с Димой подключают задачи и снимают исходное качество, ошибки, скорость и расходы.
3. **Данные:** Сергей с Вовой параллельно проверяют train-пилот, выделяют dev и собирают учительские SFT-траектории; начинается GEPA.
4. **Обучение:** после фиксации данных и промпта выполняются SFT и RL; тренировочный стек проверяется с первой недели.
5. **Оценка:** выбранные по внутреннему dev варианты сравниваются на внешних SQL/RAG/hybrid-наборах по фиксированному протоколу.

В текущем retrieval-прототипе используется Recall@10. SQL execution accuracy, retrieval и accuracy ответа оцениваются отдельно. Hybrid-задачи требуют проверки необходимости двух источников. Награда может сочетать программную проверку и LLM-судью; строгий RLVR не обязателен. Протокол — в [EXPERIMENTS.md](docs/EXPERIMENTS.md).

## Данные и воспроизводимость

**Кандидаты train:** PAUQ/BIRD train, HotpotQA train и HyDRA train после аудита; собственные hybrid-задачи при необходимости. Внутренний dev выделяется до генерации. **Оценка:** SQL — PAUQ/BIRD dev; RAG — ранее выбранные BrowseComp-Plus, TRuST, SynthComp-Ru/En; hybrid — кандидаты HyDRA dev, HybridDeepResearch и дополнительно HybridQA dev. Новые источники и состав панели фиксируем по аудиту. Внешние вопросы, эталоны и производные траектории исключены из GEPA/SFT/RL. Исследование — в [HYBRID_RESEARCH.md](docs/HYBRID_RESEARCH.md).

В Git хранятся код, конфиги, манифесты и небольшой синтетический пример. Большие корпуса, индексы, веса, траектории и артефакты находятся во внешнем или локальном хранилище. Источники данных и их версии фиксируются, оценочные вопросы и эталоны не используются для обучения.

Для экспериментов сохраняются версии кода и данных, параметры моделей, seed, промпты, лимиты, траектории, метрики и расходы. Трекинг — MLflow. Ключи API передаются через локальную конфигурацию; платные запуски имеют согласованный бюджет.
