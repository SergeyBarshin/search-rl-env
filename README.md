# search-rl-env

Разрабатываем собственный GEPA-like оптимизатор для собственного Text-to-SQL + RAG-харнесса. Между пользовательскими запросами он анализирует завершённые траектории и отбирает версии инструкций. Сначала меняются промпты, затем добавляется создание и редактирование текстовых skills. Веса модели фиксированы.

Первый результат команды — рабочий статический харнесс и воспроизводимые исходные замеры. Затем сравниваем static, Hermes-like memory-only и prompt-evolution на одном потоке. Качество определяет независимая оценка первой попытки на следующих запросах. [Архитектура](docs/RUNTIME_OPTIMIZER.md).

## Текущее состояние

Оптимизатор, постоянная память и потоковая оценка запланированы после исходных измерений. Готовность цикла самоулучшения требует сквозной проверки между сессиями; ниже описаны существующие компоненты.

Постановка описана в [AGENT_SCOPE.md](docs/AGENT_SCOPE.md). Есть многораундовый поиск свидетельств, синтетический SQL + RAG-пример, SQL/search-адаптеры, диагностический replay и агентный пилот HyDRA. Отдельный оценщик рассчитывает Recall@10 по сохранённым эпизодам текстового поиска. Следующий замер качества использует [публичные наборы](docs/EXPERIMENTS.md#план-замеров-на-публичных-наборах).

Статический харнесс использует **OpenAI Agents SDK 0.24.0**. Одиночный запуск, пакетный раннер и UI используют общий интерфейс. Публичный JSON версии 4 сохраняет историю, действия, usage и причину остановки. Приватные эталоны используются оценщиком после выполнения эпизода.

Для подключения команды начните с [передачи харнесса](docs/HARNESS_HANDOFF.md): установка, примеры RAG/SQL/hybrid, свой пакет задач, конфиги, результаты и границы ответственности. Текущий поиск и замена мока описаны в [RAG_SEARCH.md](docs/RAG_SEARCH.md).

Для разработки используем Qwen через настраиваемый Chat Completions API. Model id задаётся явно в CLI или `MODEL_ID`; для прямого OpenRouter есть отдельный режим и `OPENROUTER_MODEL`. Для первой статьи фиксируем веса модели.

## Как устроена работа

| Участник | Ответственность | Планируемые модули |
|---|---|---|
| **Сергей** | Агент, харнесс, runtime-оптимизатор и память и текст статьи | `agent/`, будущий `memory/` |
| **Дима** | SQL-база и схема таблиц, выполнение запросов, хранение корпуса, индексы и поисковые ручки | `src/search_rl_env/search/` |
| **Коля** | Инфраструктура снятия бенчмарков поверх харнесса и поиска: конфиги прогонов, возобновление, метрики, затраты и отчёты | `evaluation/` |
| **Вова** | Бенчмарки: задачи, эталоны, метрики, джаджи и проверка качества оценки | `benchmarks/` |

Ближайший результат — измерения static. Распределение работ по этапам приведено в [TASKS.md](docs/TASKS.md).

## Структура репозитория

Реализованы контракты, runtime, поисковые бэкенды, оценщики, примеры и тесты. Будущие модули отмечены в дереве.

```text
src/search_rl_env/
├── contracts/      # типы задачи, поиска, конфигурации и результата
├── agent/          # OpenAI Agents SDK, клиенты API и моки
├── environment/    # состояние эпизода, SQLite и Recall@10
├── optimizer/      # план: генерация кандидатов, replay и отбор версий
├── memory/         # план: история, постоянные записи, skills, обслуживание и версии
├── training/       # последующее расширение: SFT/RL
├── search/         # HTTP-поиск, локальные индексы, эмбеддинги и адаптер T-Search
├── benchmarks/     # план: задачи, метрики и джаджи
└── evaluation/     # независимая оценка HyDRA и текстового retrieval
examples/run_episode.py # запуск одного вопроса
examples/run_text_retrieval.py # сборка индекса, пакетный поиск и Recall@10
examples/fixtures/  # синтетический вопрос и подставная выдача без эталонов
tests/unit/agent/   # цикл, HTTP-протокол и пример запуска
docs/              # спецификации, решения и план
```

Полное дерево, владельцы и правила размещения данных — в [STRUCTURE.md](docs/STRUCTURE.md). Общие интерфейсы согласуются по примерам из [CONTRACTS.md](docs/CONTRACTS.md).

## Как начать

```bash
git clone https://github.com/SergeyBarshin/search-rl-env.git
cd search-rl-env
```

Прочитайте [правила работы](CONTRIBUTING.md), свою задачу в [TASKS.md](docs/TASKS.md) и затронутые контракты. До разработки создайте issue с результатом и способом проверки, затем рабочую ветку. Изменения вливаются в `main` через PR с ревью.

Нужен Python 3.11+. Установка из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
```

Если используете uv: `uv venv .venv`, затем `uv pip install -e '.[dev]'` и `source .venv/bin/activate`.

Бесплатный эпизод на моках:

```bash
python examples/run_episode.py --output runs/demo/episode.json
```

Ожидаемый результат: `stop_reason=finished`, документы `doc-001`, `doc-002` и JSON в указанном файле. Мок выбирает все показанные документы; это проверка взаимодействия, а не качества отбора. `runs/` исключён из Git. CLI возвращает код `0` при `finished`, `1` при остановке эпизода по другой причине.

Свой вопрос и подробный вывод в терминале:

```bash
python examples/run_episode.py --model mock \
  --question 'Какие документы описывают перенос срока проекта?' --verbose
```

`--question` заменяет вопрос в `--task`, сохраняя корпус и его ревизию. `--verbose` показывает отправку запросов, вызовы `search`/`finish` и ответы инструментов по ходу эпизода; каждые 5 секунд ожидания печатается статус, в конце — usage. Поиск возвращает фиксированную выдачу из `--hits`, поэтому для проверки результата используйте вопросы по этому синтетическому корпусу.

`--request-timeout 30` задаёт общий таймаут одного API-запроса к модели в секундах; по умолчанию — 30. При превышении сохраняется результат с `infrastructure_error` и кодом `model_timeout`. Ctrl+C завершает CLI без traceback с кодом 130 и сохраняет частичную траекторию рядом с `--output`: например, `runs/my-episode.interrupted.json`. Usage незавершённого запроса неизвестен и сохраняется как `null`; отдельный файл сохраняет прежний полный результат.

Для разрешённого запуска настоящей модели через настроенный API:

```bash
python examples/run_episode.py --model api --model-id qwen/qwen3.5-9b \
  --question 'Какие документы описывают перенос срока проекта?' --verbose \
  --max-steps 4 --max-output-tokens 2048 --max-tokens-per-step 1024 \
  --output runs/api-demo/episode.json
```

Настройте в локальном `.env` переменные `MODEL_API_URL`, `MODEL_ID` и `MODEL_API_KEY` либо `MODEL_API_KEY_FILE`. Схема заголовка авторизации задаётся через `MODEL_AUTH_SCHEME` (по умолчанию `Bearer`). Адрес и параметры доступа задаются локально; ключ не сохраняется в результате эпизода. Поиск остаётся моковым.

Модель сама выбирает запросы, число поисков и момент `finish`. Лимита поисков и остановки после нескольких ошибок нет. `--max-steps` и `--max-output-tokens` необязательны: по умолчанию оба выключены. Один запрос ограничен `--max-tokens-per-step` (512). Харнесс проверяет суммарный токенный бюджет между ходами: последний ответ может превысить его, максимум ограничивается размером ответа. Это не точный денежный лимит. При остановке по бюджету сохраняются `truncated=true` и пустой финальный список. Размер выдачи и сниппетов задаётся инструментом, порядок действий — моделью.

Seed по умолчанию не задан: некоторые доступные провайдеры Qwen его не поддерживают. `--seed 42` включает передачу seed и требует поддерживающий его маршрут; иначе API может вернуть 404 о несовместимых параметрах. Харнесс обрабатывает несколько tool calls последовательно, без требования к поддержке `parallel_tool_calls` на стороне провайдера.

Для прямого OpenRouter сохраните `OPENROUTER_API_KEY` в локальном `.env` или переменной окружения; пустой образец — [.env.example](.env.example). `.env` загружается только в режимах API и OpenRouter, переменные окружения имеют приоритет. Пример команды **для отдельно разрешённого платного запуска**; поиск остаётся моковым:

```bash
python examples/run_episode.py --model openrouter --model-id qwen/qwen3.5-9b \
  --max-steps 6 --max-output-tokens 2048 --max-tokens-per-step 512 \
  --output runs/openrouter-demo/episode.json
```

Оба клиента следуют [протоколу tool calling OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling): передают схемы при каждом запросе и возвращают результаты через `role="tool"` с исходным `tool_call_id`. Запросы не повторяются автоматически. Поддержку параметров и доступность модели проверяет провайдер; стандартные тесты не вызывают платные endpoint.

### Локальный UI для тестирования

```bash
.venv/bin/python -m search_rl_env.ui
```

Откройте [http://127.0.0.1:8866](http://127.0.0.1:8866). В интерфейсе можно выбрать сценарий «Поиск документов» или «SQL + RAG · компенсации заказов», задать вопрос, выбрать мок или модель API, посмотреть действия и результаты инструментов, остановить эпизод и скачать JSON. По умолчанию выбран мок. В сценарии SQL + RAG доступны схема и шесть строк тестовой таблицы, SQL-выдача и финальный список заказов с документами-источниками. Поиск возвращает фиксированные документы выбранного сценария. В режиме «Модель API» используются `MODEL_API_URL`, `MODEL_ID`, ключ и схема авторизации из локального `.env`; ключ в браузер не передаётся. Реальный API вызывается только после нажатия «Запустить эпизод» в этом режиме.

UI переиспользует `RolloutRunner` и общий HTTP-пул; одиночный CLI вызывает тот же цикл через `run_episode`. События поступают через SSE, полные результаты и частичные результаты отмены сохраняются в `runs/ui/<run_id>/episode.json`. Закрытие вкладки не останавливает эпизод; для этого есть кнопка «Остановить». Завершение сервера отменяет активные эпизоды. Бюджеты шагов и суммарных токенов в дополнительных параметрах по умолчанию не заданы. История запусков после перезапуска сервера в UI не восстанавливается; JSON остаётся на диске.

Если порт занят: `python -m search_rl_env.ui --port 8867`. Другой файл настроек задаётся через `--env-file`, каталог результатов — через `--output-dir`. Сервер слушает только `127.0.0.1`. Сборка фронтенда и установка npm-пакетов не нужны.

### Моковый SQL + RAG

```bash
.venv/bin/python -u examples/run_episode.py --scenario sql_rag --model mock \
  --verbose --output runs/sql-rag/episode.json
```

Связанный пример: «Какие заказы подходят под компенсацию согласно регламенту?» Поиск возвращает регламент, `sql(query)` выполняет запрос в SQLite в памяти, `finish(answer, document_ids)` возвращает id заказов и источники. Ожидаемый ответ мока — `ORD-101`, `ORD-105`; вся траектория сохраняется. У реальной модели порядок действий и запросы свободные; сценарий `search → sql → finish` запрограммирован только у моковой модели. Поиск документов как отдельный сценарий сохраняет прежний `finish(document_ids)`.

Для модели API у той же команды замените `--model mock` на `--model api`. В UI выберите сценарий SQL + RAG и режим «Модель API». Данные остаются синтетическими, ключи читаются из `.env`. Во время разработки платных вызовов не было.

Для размеченных синтетических задач оценщик сравнивает множество id ответа с приватным эталоном. Результат оценки доступен в сводке прогона.

### Параллельные роллауты

```bash
.venv/bin/python -u examples/run_rollouts.py --model mock --scenario sql_rag \
  --episodes 64 --concurrency 16 --output runs/parallel
```

Команда сохраняет отдельный `EpisodeResult` с публичной траекторией на каждый вопрос и `summary.json`: пропускная способность, p50/p95 времени эпизода, разбивка модели/инструментов/обвязки, причины остановки и награда. Для проверки транспорта используется один синтетический вопрос с разными task id. Это не оценка качества модели. `--no-save` отключает запись эпизодов для замера скорости; `--mock-latency-ms 30` добавляет ожидание каждого ответа мока. `--model api` использует `.env` и общий клиент модели.

В Python используйте один `async with RolloutRunner(model, search, config, sql=sql, concurrency=16)` на серию; `runner.run(task)` запускает один эпизод, `runner.iter_episodes(tasks)` выдаёт результаты по мере готовности. Допустимы обычные и асинхронные источники. Для приватных эталонов и индивидуального конфига есть `RolloutRequest`. Число workers и размер буфера ограничены параллельностью; при досрочном выходе закрывайте iterator через `contextlib.aclosing`. Поиск, SQL и модель заимствуются, их клиенты закрывает вызывающий код. Пример интеграции — в [CONTRACTS.md](docs/CONTRACTS.md).

Транспорт SDK и клиент провайдера переиспользуются на протяжении серии. Каждый эпизод получает своё состояние, историю и инструменты. Переход описан в [OPENAI_AGENTS_MIGRATION.md](docs/OPENAI_AGENTS_MIGRATION.md).

### Текстовый поиск с Jina и FAISS

`scripts/serve-jina-embeddings.sh` настроен на Jina v5 Small Retrieval Q4_K_M через `llama.cpp` с Metal на `127.0.0.1:8081/v1`. Сервер считает векторы, а команда сборки записывает векторы документов в FAISS. `dense` ищет в FAISS, `bm25` — в SQLite FTS5, `hybrid` объединяет обе выдачи через RRF. Снимки открываются один раз на прогон. [Архитектура поиска](docs/RAG_SEARCH.md) · [Команды и замеры](docs/EXPERIMENTS.md#закрытый-бенчмарк-текстового-поиска).

На первых 100 вопросах BrowseComp-Plus EN прямой Lucene/BM25 дал Recall@10 1,19%, прямой Qwen3-Embedding-8B с FAISS — 21,89%, агент Qwen3.6-35B-A3B с тем же FAISS — 41,90%. Агентный CLI выполняет короткие уточняющие запросы и выделяет последний ход для отбора собранных документов. [Агентный режим](docs/EXPERIMENTS.md#агентный-поиск-с-отдельной-финализацией) · [Таблица измерений](docs/EXPERIMENTS.md#измерения-от-18-ноября-2026).

### Профилирование эпизодов

В UI раздел «Профиль времени» разделяет запуск среды, запросы модели, инструменты, финализацию, оценку и прочую обвязку. В каждом API-шаге раскрывается HTTP-профиль: подготовка запроса, TCP/DNS, TLS, отправка, ожидание заголовков, первый декодированный байт тела, чтение и разбор JSON. Сохраняются статусы, размеры, request ID, доступные числовые Server-Timing и признак переиспользования соединения. У мока HTTP-замеры отсутствуют.

API пока возвращает готовый JSON (`stream=false`): время первого байта **не является TTFT**. Ожидание заголовков может включать очередь и генерацию. Они различаются только если сервер сообщает собственные метрики. Первый транспортный callback включает подготовку HTTPX и возможное ожидание пула; это не отдельный точный замер пула или DNS.

Рядом с результатом UI создаёт `runs/ui/<run_id>/events.jsonl`; его можно скачать кнопкой «Лог JSONL». В журнале есть временные отметки, episode/run/request id, шаги и длительности; сырые заголовки, тела запросов и результаты инструментов в него не копируются. Полная траектория остаётся в `episode.json`. Частичные HTTP-замеры сохраняются при отмене и таймауте. Сводку текущих запусков можно получить через `GET /api/runs`.

CLI с `--verbose` показывает фазы и итоговую разбивку; JSONL записывается рядом с `--output`, путь можно задать через `--event-log`. Разбор уже сохранённого эпизода без нового инференса:

```bash
.venv/bin/python -m search_rl_env.profiling runs/demo/episode.json
```

Для старых JSON выводятся доступные суммарные замеры; деталей HTTP задним числом не появляется. В UI один AsyncClient и keep-alive пул живут между эпизодами. `run_episode` допускает независимые параллельные вызовы; runner управляет их количеством. При прямом API-запуске общий `httpx.AsyncClient` передаётся через `http_client`, его закрывает создавший runner. Изоляция состояний и HTTP-профилей при таком запуске проверена тестом.

Проверки:

```bash
python -m pytest -q
git diff --check
```

Тесты покрывают несколько поисков по решению модели, нормальное завершение, бюджеты, повторы id, неизвестные документы, исправление ошибочных действий, сбои, JSON-сохранение и воспроизведение. HTTP-вызовы OpenRouter проверяются через `httpx.MockTransport`, без сети. Точные интерфейсы для поиска Димы и runner Коли — в [CONTRACTS.md](docs/CONTRACTS.md).

## Python-бэкенд SQL и поиска

Сервис реализован в `search_rl_env.search.server` на aiohttp и стандартной sqlite3.
Для HTTP API достаточно основной установки проекта; FAISS нужен для изолированных сред.

Пилот HyDRA использует десять параллельных эпизодов с SQLite и отдельным
локальным BM25 + FAISS на хешированных словах. Порядок подготовки, запуск через
Eliza с согласованным бюджетом, HTML-траектории и пересчёт оценок описаны в
[HYDRA_PILOT.md](docs/HYDRA_PILOT.md).

```bash
python -m search_rl_env.search.server build
python -m search_rl_env.search.server serve --sql-catalog configs/backend/sql-catalog.example.json
```

SQL-пример требует подготовленной BIRD-базы: `python examples/prepare_hydra.py`.
Для SQL-only используйте `serve-sql --sql-catalog PATH`. Каталог содержит пути
к SQLite и SHA-256; SDK SQLClientPool выбирает БД и ревизию для задачи.

Поиск и чтение: `python examples/run_search.py search --query 'Toronto Arenas'`.
SQL и поиск на одной HyDRA-задаче: `python examples/run_hydra.py`.
Это replay с эталонным SQL, не самостоятельное решение агентом.
Подробности — в [SEARCH_BACKEND.md](docs/SEARCH_BACKEND.md),
[SQL_BACKEND.md](docs/SQL_BACKEND.md), [HYDRA_PILOT.md](docs/HYDRA_PILOT.md).

## Приёмка 40 изолированных SQLite/FAISS-сред

Полная проверка в Docker (Colima на Mac):

```bash
sh scripts/check-docker.sh
```

Команда запускает Colima при необходимости, собирает CPU-образ Python 3.12,
выполняет полный pytest и сравнение 1/40. Логи, JUnit, версии пакетов и артефакты
сохраняются в новом каталоге `runs/docker/`. Сборке нужен доступ к registry и PyPI;
проверки внутри контейнера выполняются без внешней сети. Ключи API не нужны.

Для повторной проверки только pytest после исправления теста:
`sh scripts/check-docker.sh --tests-only`. Уже успешный замер 1/40 не повторяется;
в checks.json пропущенный этап имеет acceptance_exit_code=null.

```bash
python -m pip install -e '.[dev,environments]'
python examples/accept_environments.py
```

Это бесплатный технический сценарий через публичный харнесс: собственные SQLite
и FAISS на эпизод, два разных набора с совпадающими doc_id, прогрев и сравнение
параллельностей 1/40. Веса моделей не нужны. Фабрика сред закрывает native-workers,
соединения, индексы и временные файлы; результаты, ревизии, метрики и частичные
траектории сохраняются в новом каталоге runs/environments.

Изолированный адаптер использует реальные SQLite/FAISS непосредственно; Python HTTP API
проверяется отдельно. Установка CPU-зависимостей обязательна: при отсутствии FAISS
подмена не выполняется. Подключение другого набора, формат передачи Коле,
ограничения измерений и отдельный разрешаемый OpenRouter-запуск описаны в
[ISOLATED_ENVIRONMENTS.md](docs/ISOLATED_ENVIRONMENTS.md).

## Первый совместный результат

Первый результат команды — рабочий статический харнесс и воспроизводимые исходные замеры. Затем сравниваем static, Hermes-like memory-only и prompt-evolution на одном потоке. Качество определяет независимая оценка первой попытки на следующих запросах.

В основном эксперименте адаптации доступны запрос, ответ, публичные вызовы и результаты инструментов, ошибки и суждения внутреннего критика. Эталонный SQL, ответы, метки документов, benchmark reward и оценки исследователей доступны только независимому оценщику. Исправления с правильным ответом допустимы в отдельном явно обозначенном эксперименте. [План разработки](docs/ROADMAP.md).

## Данные и воспроизводимость

Открытая панель: HyDRA как первый hybrid-кандидат, BIRD/PAUQ и HotpotQA для SQL/RAG-диагностики. Дополнительные наборы выбираются по доступности, правилам и оценщикам. Реестр — [HYBRID_RESEARCH.md](docs/HYBRID_RESEARCH.md). Gold SQL replay проверяет инструменты и не считается самостоятельным качеством агента.

Собственный бенчмарк задаёт сессии с повторяющимися ситуациями, новыми вопросами, исправлениями пользователя, сменой данных/схем и проверками сохранения/забывания опыта. Эталоны и будущие события скрыты; политика feedback раскрыта и одинакова у сравниваемых вариантов. Семейства разработки/dev/закрытой оценки разделяются до генерации производных данных.

Версии памяти, прочитанные записи и события answer/score/feedback/update связываются с нативными траекториями. Код, конфиги, манифесты и небольшие fixtures хранятся в Git; большие данные, история и snapshots — в локальном или внешнем хранилище. Целевой трекинг — MLflow. Ключи остаются локальными; платные API/cloud/GPU требуют отдельного бюджета.

SFT/RL, сервинг дообученных весов и универсальный генератор сред — дальнейшее развитие. GEPA и опубликованные методы памяти — кандидаты дополнительных сравнений. Основной продукт — харнесс и методика.
