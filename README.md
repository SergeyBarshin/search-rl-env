# search-rl-env

Проект открытой RL-среды для обучения поисковых агентов по фиксированному корпусу документов. Агент получает вопрос, обращается к поиску, собирает свидетельства и возвращает результат. Среда предоставляет инструменты, траектории и оценку.

На собственном агенте покажем обучение в этой среде: исходное качество, кривые обучения и результат на отложенных задачах. Рост метрики проверяется на вопросах, которые не использовались для обновления модели.

## Текущее состояние

Харнесс работает на **Verifiers 0.4.0, API `verifiers.v1`**: `Taskset` загружает задачи, `Task` задаёт инструменты и награду, `Harness` запускает штатный chat loop Verifiers. Публичная функция `run_episode(task, model, search, config)` сохранена. Есть моки, настраиваемый Chat Completions API, OpenRouter, терминальный прогресс и JSON с нативной `Trace`. Для размеченных задач считается Recall@10; без эталонов награда равна `null`. Проверки работают без внешних API, весов и GPU; локальные MCP/HTTP-серверы запускает Verifiers. Обновление весов, реальный поиск и MLflow ещё не подключены.

Для разработки используем Qwen через настраиваемый Chat Completions API. Model id задаётся явно в CLI или `MODEL_ID`; для прямого OpenRouter есть отдельный режим и `OPENROUTER_MODEL`. Пример RL-обучения затем подключается к весам модели в тренировочном окружении.

## Как устроена работа

| Участник | Ответственность | Планируемые модули |
|---|---|---|
| **Сергей** | Агент, харнесс и модели: цикл действий, промпты, контекст, клиенты моделей, ограничения эпизода и RL | `agent/`, `training/` |
| **Дима** | База данных и поиск: хранение корпуса, индексы, поисковые ручки и чтение документов | `search/` |
| **Коля** | Инфраструктура снятия бенчмарков поверх харнесса и поиска: конфиги прогонов, возобновление, метрики, затраты и отчёты | `evaluation/` |
| **Вова** | Бенчмарки: задачи, эталоны, метрики, джаджи и проверка качества оценки | `benchmarks/` |

Инфраструктура Коли запускает задачи Вовы через харнесс Сергея. Агент обращается к поиску Димы. Результаты проходят через оценщики Вовы, а runner сохраняет оценки и отчёт. Подробные первые задачи — в [TASKS.md](docs/TASKS.md).

## Структура репозитория

Реализованы `contracts/`, `agent/`, `environment/`, пример и тесты. Остальные компоненты ниже остаются планом:

```text
src/search_rl_env/
├── contracts/      # типы задачи, поиска, конфигурации и результата
├── agent/          # запуск Verifiers, клиенты API, моки и совместимый адаптер
├── environment/    # Taskset, Task, MCP-инструменты, состояние и Recall@10
├── training/       # план: обучение
├── search/         # план: корпус и поиск
├── benchmarks/     # план: задачи, метрики и джаджи
└── evaluation/     # план: прогоны и отчёты
examples/run_episode.py # запуск одного вопроса
examples/fixtures/  # синтетический вопрос и подставная выдача без эталонов
tests/unit/agent/   # цикл, HTTP-протокол и пример запуска
docs/              # спецификации, решения и план
```

Полное дерево, владельцы и правила размещения данных — в [STRUCTURE.md](docs/STRUCTURE.md). Общие интерфейсы согласуются по примерам из [CONTRACTS.md](docs/CONTRACTS.md).

## Как начать

```bash
git clone https://github.com/SergeyBarshin/search-rl-env.git
cd search-rl-env
```

Прочитайте [правила работы](CONTRIBUTING.md), свою задачу в [TASKS.md](docs/TASKS.md) и затронутые контракты. До разработки создайте issue с результатом и способом проверки, затем рабочую ветку. Изменения вливаются в `main` через PR с ревью.

Нужен Python 3.11+. Установка из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
```

Если используете uv: `uv venv .venv`, затем `uv pip install -e '.[dev]'` и `source .venv/bin/activate`.

Бесплатный эпизод на моках:

```bash
python examples/run_episode.py --output runs/demo/episode.json
```

Ожидаемый результат: `stop_reason=finished`, документы `doc-001`, `doc-002` и JSON в указанном файле. Мок выбирает все показанные документы; это проверка взаимодействия, а не качества отбора. `runs/` исключён из Git. CLI возвращает код `0` при `finished`, `1` при остановке эпизода по другой причине.

Свой вопрос и подробный вывод в терминале:

```bash
python examples/run_episode.py --model mock \
  --question 'Какие документы описывают перенос срока проекта?' --verbose
```

`--question` заменяет вопрос в `--task`, сохраняя корпус и его ревизию. `--verbose` показывает отправку запросов, вызовы `search`/`finish` и ответы инструментов по ходу эпизода; каждые 5 секунд ожидания печатается статус, в конце — usage. Поиск возвращает фиксированную выдачу из `--hits`, поэтому для проверки результата используйте вопросы по этому синтетическому корпусу.

`--request-timeout 30` задаёт общий таймаут одного API-запроса к модели в секундах; по умолчанию — 30. При превышении сохраняется результат с `infrastructure_error` и кодом `model_timeout`. Ctrl+C завершает CLI без traceback с кодом 130 и сохраняет частичную траекторию рядом с `--output`: например, `runs/my-episode.interrupted.json`. Usage незавершённого запроса неизвестен и сохраняется как `null`; отдельный файл сохраняет прежний полный результат.

Для разрешённого запуска настоящей модели через настроенный API:

```bash
python examples/run_episode.py --model api --model-id qwen/qwen3.5-9b \
  --question 'Какие документы описывают перенос срока проекта?' --verbose \
  --max-steps 4 --max-output-tokens 2048 --max-tokens-per-step 1024 \
  --output runs/api-demo/episode.json
```

Настройте в локальном `.env` переменные `MODEL_API_URL`, `MODEL_ID` и `MODEL_API_KEY` либо `MODEL_API_KEY_FILE`. Схема заголовка авторизации задаётся через `MODEL_AUTH_SCHEME` (по умолчанию `Bearer`). Адрес и параметры доступа задаются локально; ключ не сохраняется в результате эпизода. Поиск остаётся моковым.

Модель сама выбирает запросы, число поисков и момент `finish`. Лимита поисков и остановки после нескольких ошибок нет. `--max-steps` и `--max-output-tokens` необязательны: по умолчанию оба выключены. Один запрос ограничен `--max-tokens-per-step` (512). Verifiers проверяет суммарный токенный бюджет между ходами: последний ответ может превысить его, максимум ограничивается размером ответа. Это не точный денежный лимит. При остановке по бюджету сохраняются `truncated=true` и пустой финальный список. Размер выдачи и сниппетов задаётся инструментом, порядок действий — моделью.

Seed по умолчанию не задан: некоторые доступные провайдеры Qwen его не поддерживают. `--seed 42` включает передачу seed и требует поддерживающий его маршрут; иначе API может вернуть 404 о несовместимых параметрах. Харнесс обрабатывает несколько tool calls последовательно, без требования к поддержке `parallel_tool_calls` на стороне провайдера.

Для прямого OpenRouter сохраните `OPENROUTER_API_KEY` в локальном `.env` или переменной окружения; пустой образец — [.env.example](.env.example). `.env` загружается только в режимах API и OpenRouter, переменные окружения имеют приоритет. Пример команды **для отдельно разрешённого платного запуска**; поиск остаётся моковым:

```bash
python examples/run_episode.py --model openrouter --model-id qwen/qwen3.5-9b \
  --max-steps 6 --max-output-tokens 2048 --max-tokens-per-step 512 \
  --output runs/openrouter-demo/episode.json
```

Оба клиента следуют [протоколу tool calling OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling): передают схемы при каждом запросе и возвращают результаты через `role="tool"` с исходным `tool_call_id`. Запросы не повторяются автоматически. Поддержку параметров и доступность модели проверяет провайдер; стандартные тесты не вызывают платные endpoint.

Нативный запуск Verifiers и проверка конфигурации без инференса:

```bash
.venv/bin/vf-eval @ configs/verifiers-eval.toml --dry-run
.venv/bin/vf-eval @ configs/verifiers-train-rollout.toml --dry-run
```

Первый конфиг использует Chat Completions, второй — тренировочный клиент с renderer Qwen3.5 и vLLM `/inference/v1/generate`. Для фактического запуска нужен подготовленный сервер и разрешённый бюджет; `--dry-run` только проверяет конфиг. В обоих примерах `push=false`, результаты остаются локально. Конфиги не читают `.env` автоматически: переменные авторизации должны быть в окружении.

Набор по умолчанию синтетический, поиск — моковый. `env.taskset.tasks_path` принимает JSON со списком задач и необязательными `reference_document_ids`; эталоны не включаются в промпт. Для обучения задайте **отдельный train-файл**, `require_references=true`, а dev/test запускайте отдельно. Конфиг `verifiers-train-rollout.toml` собирает траектории, обновление весов выполняет внешний тренер. Схема и границы компонентов — в [CONTRACTS.md](docs/CONTRACTS.md), архитектура и сценарии проверки — в [HARNESS_REPORT.md](docs/HARNESS_REPORT.md).

Проверки:

```bash
python -m pytest -q
git diff --check
```

Тесты покрывают несколько поисков по решению модели, нормальное завершение, бюджеты, повторы id, неизвестные документы, исправление ошибочных действий, сбои, JSON-сохранение и воспроизведение. HTTP-вызовы OpenRouter проверяются через `httpx.MockTransport`, без сети. Точные интерфейсы для поиска Димы и runner Коли — в [CONTRACTS.md](docs/CONTRACTS.md).

## Первый совместный результат

1. **Общий пример:** Вова готовит небольшой синтетический корпус, вопросы, эталоны и примеры оценок.
2. **Контракты:** Сергей и Дима согласуют поиск; Сергей и Коля — вызов харнесса; Вова и Коля — оценщики.
3. **Компоненты:** поиск отвечает по корпусу, агент проходит один эпизод, runner сохраняет результат и считает метрику.
4. **Исходная оценка:** одинаковый набор запускается по конфигу с сохранением траекторий и затрат.
5. **Обучение:** подключается тренировочный цикл, затем сравниваются исходная и обученная модели.

Для первого retrieval-примера предложен Recall@10. Конкретные задачи, единица оценки и награда остаются предметом спецификации; фиксация происходит до сравнительного прогона. План проверки — в [EXPERIMENTS.md](docs/EXPERIMENTS.md).

## Данные и воспроизводимость

В Git хранятся код, конфиги, манифесты и небольшой синтетический пример. Большие корпуса, индексы, веса, траектории и артефакты находятся во внешнем или локальном хранилище. Источники данных и их версии фиксируются, оценочные вопросы и эталоны не используются для обучения.

Для экспериментов сохраняются версии кода и данных, параметры моделей, seed, промпты, лимиты, траектории, метрики и расходы. Трекинг — MLflow. Ключи API передаются через локальную конфигурацию; платные запуски имеют согласованный бюджет.
