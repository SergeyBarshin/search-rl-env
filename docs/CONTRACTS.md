# Границы компонентов и общие форматы

Рабочий проект от 2026-10-31. Этот документ задаёт минимальные договорённости для параллельной разработки. Точные Python-типы, синхронность вызовов и HTTP-схемы фиксируются первым интеграционным PR; имена ниже иллюстрируют контракт.

## Задача и эталон

Вова готовит задачу с постоянным `task_id`, вопросом, языком, корпусом, версией и split. Для загрузчика и оценщика доступны эталонные id, допустимые ответы и правила проверки. Агент получает отдельное представление задачи без эталонных полей.

Пример исходной записи для детерминированной retrieval-задачи:

```json
{
  "task_id": "demo-001",
  "question": "Какой документ описывает перенос срока проекта?",
  "language": "ru",
  "corpus_id": "synthetic-demo",
  "corpus_revision": "v1",
  "split": "dev",
  "gold": {"relevant_doc_ids": ["doc-002"]}
}
```

При передаче вопроса модели поле `gold` исключается. Это синтетический пример, а не часть внешнего оценочного набора.

## Харнесс и поиск

Владельцы — Сергей и Дима. Минимальные операции:

- поиск по запросу с явным корпусом, его ревизией и ограничением числа результатов;
- получение текста по известному id с ограничением объёма возвращаемого текста;
- единый формат ожидаемых ошибок и технической телеметрии.

Каждый результат поиска содержит `doc_id`, при наличии чанков — `chunk_id`, показанный текст и позицию в выдаче. Значение score и его смысл задаёт бэкенд; оно не приравнивается к вероятности релевантности. Количество результатов, длина сниппета и порядок обрезки определяются конфигом. Неизвестный id и недоступный бэкенд различаются явно.

Состояние диалога и выбор следующего действия принадлежат харнессу. Поисковые ручки не вызывают языковую модель для управления агентом.

## Запуск бенчмарка и харнесс

Владельцы — Коля и Сергей. Runner передаёт одну разрешённую задачу, конфигурацию агента, бюджет и seed. Харнесс возвращает результат эпизода и траекторию.

В результате нужны `task_id`, `episode_id`, причина завершения, ранжированные id документов и при наличии финальный ответ. Отдельно сохраняются вызовы инструментов, токены, время и доступные расходы. Настройки и версии моделей, корпуса и кода записываются на уровне прогона. Идентификатор повторной попытки позволяет отличить её от нового вопроса.

Для возобновления runner учитывает завершённые задачи и их конфигурацию. Нельзя подхватить результаты от другого корпуса или модели только потому, что совпал `task_id`. Пропуски и инфраструктурные ошибки не исчезают из отчёта.

## Оценщики и runner

Владельцы — Вова и Коля. Оценщик получает результат эпизода и доступный только ему эталон. Возвращает численные метрики, статус оценки и диагностическую информацию. Он может работать по сохранённому результату без нового вызова агента.

Детерминированная метрика и LLM-джадж могут иметь разные конфиги. Для джаджа фиксируются модель, промпт, параметры, токены и расходы. Ошибка джаджа отличается от отрицательной оценки ответа. Набор, метрика, судья и их версии входят в идентификатор оценочного прогона.

## Изменения контракта

Пример входа, ожидаемый выход и проверка совместимости входят в тот же PR, что и изменение. Несовместимое изменение согласуется с владельцами обеих сторон и сопровождается обновлением версии формата. До первой реализации эти договорённости проверяются на одном ручном эпизоде.
