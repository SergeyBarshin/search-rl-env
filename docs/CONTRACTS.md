# Границы компонентов и общие форматы

Версия первого Python-контракта от 2026-10-31: `EpisodeResult.schema_version="1"`. Типы реализованы в `src/search_rl_env/contracts/types.py`, цикл — в `src/search_rl_env/agent/loop.py`. HTTP-контракт реального поиска пока не задан; харнесс использует async-интерфейс Python.

## Задача и эталон

Вова готовит задачу с постоянным `task_id`, вопросом, языком, корпусом, версией и split. Для загрузчика и оценщика доступны эталонные id, допустимые ответы и правила проверки. Агент получает отдельное представление задачи без эталонных полей.

Пример исходной записи для детерминированной retrieval-задачи:

```json
{
  "task_id": "demo-001",
  "question": "Какой документ описывает перенос срока проекта?",
  "language": "ru",
  "corpus_id": "synthetic-demo",
  "corpus_revision": "v1",
  "split": "dev",
  "gold": {"relevant_doc_ids": ["doc-002"]}
}
```

Загрузчик явно создаёт `AgentTask` из разрешённых полей: `task_id`, `question`, `language`, `corpus_id`, необязательный `corpus_revision`. Неизвестные поля, включая `gold` и `split`, отклоняются валидатором, а не молча удаляются. Split и эталоны остаются у runner и оценщика. Это синтетический пример, а не часть внешнего оценочного набора.

## Харнесс и поиск

Владельцы — Сергей и Дима. Минимальные операции:

- поиск по запросу с явным корпусом, его ревизией и ограничением числа результатов;
- получение текста по известному id с ограничением объёма возвращаемого текста;
- единый формат ожидаемых ошибок и технической телеметрии.

Каждый результат поиска содержит `doc_id`, при наличии чанков — `chunk_id`, показанный текст и позицию в выдаче. Значение score и его смысл задаёт бэкенд; оно не приравнивается к вероятности релевантности. Количество результатов, длина сниппета и порядок обрезки определяются конфигом. Неизвестный id и недоступный бэкенд различаются явно.

В первой реализации есть только поиск. Получение полного текста, `chunk_id`, score и телеметрия бэкенда остаются будущим расширением. `SearchHit` сейчас содержит ровно `doc_id: str`, `snippet: str`, `rank: int` (позиция от 1). Бэкенд возвращает упорядоченный список; харнесс сохраняет порядок и позиции, удаляет повторные `doc_id` в одной выдаче, оставляет первые `search_limit` уникальных документов и обрезает каждый сниппет до `max_snippet_chars` символов. Только показанные id разрешены в `finish`.

Интерфейс для Димы:

```python
from search_rl_env.contracts import SearchHit

class SearchBackend:
    async def search(
        self,
        query: str,
        *,
        corpus_id: str,
        corpus_revision: str | None,
        limit: int,
    ) -> list[SearchHit]:
        ...
```

Корпус и ревизия всегда передаются из задачи, модель не может переопределить их аргументами инструмента. Исключение или невалидная выдача бэкенда останавливают эпизод с `infrastructure_error` и кодом `search_error`. Стабильные коды ошибок реального поиска согласуем с его первым адаптером. В результат не попадает произвольный текст исключения с возможными credentials.

Состояние диалога принадлежит харнессу; запрос и момент завершения выбирает модель. Поисковые ручки не вызывают языковую модель для управления агентом.

## Запуск бенчмарка и харнесс

Владельцы — Коля и Сергей. Runner передаёт одну разрешённую задачу, конфигурацию агента, бюджет и seed. Харнесс возвращает результат эпизода и траекторию.

Интерфейс для Коли:

```python
from search_rl_env.agent import run_episode, save_episode
from search_rl_env.contracts import AgentTask, EpisodeConfig

task = AgentTask(
    task_id="demo-001",
    question="Какие документы описывают перенос срока проекта?",
    language="ru",
    corpus_id="synthetic-demo",
    corpus_revision="v1",
)
# model реализует ChatModel, search — SearchBackend.
result = await run_episode(task, model, search, EpisodeConfig(seed=42))
save_episode(result, f"runs/demo/{result.episode_id}.json")
```

`run_episode` не пишет на диск и не запускает оценщик. Необязательный keyword-аргумент `on_event` принимает синхронный callback для `EpisodeEvent`: `kind`, `step`, `details`. События `model_started`, `model_finished`, `tool_started`, `tool_finished` отправляются по ходу выполнения; данные события копируются перед передачей наблюдателю. Вызов с прежними четырьмя аргументами сохраняет поведение без вывода прогресса.

При отмене `run_episode` вызывает необязательный синхронный callback `on_interrupted(partial_result)` и повторно поднимает исходный `asyncio.CancelledError`, сохраняя стандартную семантику отмены и внешнего `asyncio.timeout`. Частичный результат имеет `stop_reason="infrastructure_error"`, `error.code="interrupted"`. Завершённые шаги сохраняют usage; если запрос модели прерван до ответа, итоговый usage содержит `null`. Прерванный инструмент получает запись с ошибкой `interrupted`. Такой снимок предназначен для диагностики, автоматическое продолжение по нему не реализовано.

`save_episode` атомарно записывает UTF-8 JSON по выбранному runner пути, заменяя существующий файл. Обратное чтение: `EpisodeResult.model_validate_json(path.read_text(encoding="utf-8"))`. Новый запуск получает новый `episode_id`; привязка попыток к прогону и возобновление принадлежат runner. CLI обрабатывает отмену без traceback, сохраняет снимок в отдельный `*.interrupted.json` и возвращает код 130.

При запуске примера из README проекция результата имеет вид:

```json
{
  "schema_version": "1",
  "task_id": "demo-001",
  "selected_document_ids": ["doc-001", "doc-002"],
  "stop_reason": "finished",
  "truncated": false,
  "search_calls": 1
}
```

Полный `EpisodeResult` дополнительно содержит `episode_id`, `task`, `config`, `model_metadata`, полную `history`, пошаговую `trajectory`, суммарный `usage`, `invalid_actions`, `started_at`, `duration_seconds` и необязательный `error`. В траектории каждого шага есть usage провайдера, model/provider/response id, finish reason, запрошенный лимит выходных токенов, время модели, вызовы инструментов с исходными аргументами, ответами и длительностью. История сохраняет assistant-сообщения с reasoning-полями провайдера и все tool-ответы с `tool_call_id`. Поля `prompt_tokens`, `completion_tokens`, `total_tokens`, `cost` суммируются; если значение отсутствовало хотя бы в одном ответе, итог по этому полю равен `null`. В отдельном шаге сохраняются доступные подробности usage. Cost — расходы, сообщённые OpenRouter; харнесс не пересчитывает их по прайсу.

`model_metadata` не содержит ключа API. Для настраиваемого API сохраняется `adapter="chat-completions"` и endpoint её прокси, для прямого OpenRouter — `adapter="openrouter-chat-completions"`. Ревизии кода, индекса, модели, split, id прогона и MLflow tracking добавляет runner; в первом PR эта интеграция не реализована. Seed передаётся модели и сохраняется в конфиге, но сам по себе не гарантирует детерминизм внешнего провайдера. Адаптер может поднять `ModelError` с безопасным для журнала текстом; например, HTTP-статус сохраняется, тело ошибочного API-ответа — нет. Произвольные исключения сохраняются только по имени класса.

### Действия и остановка

`search(query: str)` возвращает `{"ok": true, "hits": [...]}`. `finish(document_ids: list[str])` принимает только ранее показанные id, удаляет повторы с сохранением порядка и возвращает `{"ok": true, "document_ids": [...]}`. Пустой список допустим. Финальный список длиннее `max_documents` отклоняется. Ошибки имеют вид `{"ok": false, "error": {"code": "...", "message": "..."}}` и возвращаются модели через `role="tool"` с соответствующим `tool_call_id`.

Модель сама решает, когда искать, повторять поиск и завершать эпизод. Как в [Search-R1](https://github.com/PeterGriffinJin/Search-R1/blob/main/search_r1/llm_agent/generation.py), внешний бюджет ограничивает длину rollout. В нашем API используются Chat Completions tool calls; теги `<search>/<answer>` из Search-R1 не требуются. Эталонов и награды в наблюдении нет, результаты инструментов отделены от действий модели по ролям сообщений. RL loss masking будет реализован в тренировочном адаптере.

| Настройка | По умолчанию | Семантика |
|---|---|---|
| `max_steps` | 6 | Число ответов модели, включая ошибочные; batch tool calls считается одним шагом |
| `max_output_tokens` | 2048 | Общие completion tokens, включая reasoning, если провайдер учитывает их в usage |
| `max_tokens_per_step` | 512 | Лимит запроса: минимум этого значения и оставшегося общего бюджета |
| `max_searches` | `None` | Без отдельного лимита; число можно задать для конкретного прогона, 0 запрещает поиск |
| `max_invalid_actions` | 2 | Суммарное число ошибочных действий до принудительной остановки |
| `search_limit` | 10 | Максимум уникальных документов в одном наблюдении |
| `max_snippet_chars` | 2000 | Максимум символов в одном сниппете |
| `max_documents` | 10 | Максимум уникальных id в финальном списке |
| `seed` | `None` | Передаётся только при явном указании; требует поддержки провайдером |

После последнего разрешённого поиска ещё разрешён `finish`; следующий запрос поиска останавливает эпизод. При нескольких tool calls они выполняются по порядку, каждый с проверкой лимитов. После `finish` и принудительной остановки оставшиеся вызовы получают `episode_stopped` без выполнения.

`stop_reason`: `finished`, `max_steps`, `max_searches`, `max_output_tokens`, `invalid_action` или `infrastructure_error`. При исчерпании бюджета `truncated=true`; итоговый список пуст, показанные документы доступны в истории. Финализация не вызывает дополнительную модель и не выдаёт все найденные документы за её выбор. Точный `finish` на границе общего токенного бюджета допустим. Ответ с `finish_reason=length` считается обрезанным, его инструменты не выполняются.

Неправильные аргументы, неизвестный инструмент или непоказанные id дают модели возможность исправиться до `max_invalid_actions`, расходуя шаги и токены. Нарушение структуры tool calls или повтор `tool_call_id` сразу останавливает эпизод: продолжать такой диалог по API нельзя. При отсутствии `completion_tokens` эпизод завершается инфраструктурной ошибкой `missing_usage`, поскольку остаток бюджета неизвестен. Автоповторов платных запросов нет. Адаптеры настраиваемого API и OpenRouter ограничивают полное время HTTP-запроса через `timeout_seconds`, включая ожидание заголовков и тела ответа. Таймаут даёт `infrastructure_error` с кодом `model_timeout`, его значение сохраняется в `model_metadata`. CLI задаёт его через `--request-timeout`, по умолчанию 30 секунд; при создании клиента напрямую по умолчанию 60 секунд.

Для возобновления runner учитывает завершённые задачи и их конфигурацию. Нельзя подхватить результаты от другого корпуса или модели только потому, что совпал `task_id`. Пропуски и инфраструктурные ошибки не исчезают из отчёта.

## Оценщики и runner

Владельцы — Вова и Коля. Оценщик получает результат эпизода и доступный только ему эталон. Возвращает численные метрики, статус оценки и диагностическую информацию. Он может работать по сохранённому результату без нового вызова агента.

Детерминированная метрика и LLM-джадж могут иметь разные конфиги. Для джаджа фиксируются модель, промпт, параметры, токены и расходы. Ошибка джаджа отличается от отрицательной оценки ответа. Набор, метрика, судья и их версии входят в идентификатор оценочного прогона.

## Изменения контракта

Пример входа, ожидаемый выход и проверка совместимости входят в тот же PR, что и изменение. Несовместимое изменение согласуется с владельцами обеих сторон и сопровождается обновлением версии формата. До первой реализации эти договорённости проверяются на одном ручном эпизоде.
