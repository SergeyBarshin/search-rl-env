# Целевая постановка Text-to-SQL + RAG

Сергей уточнил архитектуру 2026-10-31: агент использует SQL для структурированных данных и поиск для документов. Среда предоставляет инструменты, наблюдения, журнал и оценку. Порядок и число действий определяет модель.

Текущий прототип реализует поиск и выбор id документов с Recall@10. В рабочем дереве также добавлены синтетическое SQL + RAG демо, SQLite-бэкенд и ответ списком id. Контракт версии 3 описан в [CONTRACTS.md](CONTRACTS.md); общий формат ответов и реальный SQL-бэкенд требуют дальнейшей интеграции.

## Архитектура и данные эксперимента

Оценка включает **SQL-only, RAG-only и hybrid**. Ранее выбранные BrowseComp-Plus, TRuST, SynthComp-Ru/En сохраняются для RAG. Для SQL рассматриваем PAUQ/BIRD, для hybrid — HyDRA dev и HybridDeepResearch, дополнительно HybridQA dev. Состав новых наборов фиксируем после аудита источников и оценщиков, до сравнительных прогонов.

Рабочие train-источники: PAUQ/BIRD train, HotpotQA train и HyDRA train после проверки качества. Собственные hybrid-задачи добавляем при необходимости. До генерации выделяем внутренний dev и проверяем пересечения исходных и производных вопросов. GEPA, SFT и RL используют разные продукты из общего пула: задачи/feedback, проверенные траектории учителя и задачи/reward соответственно. Протокол — в [EXPERIMENTS.md](EXPERIMENTS.md), аудит — в [HYBRID_RESEARCH.md](HYBRID_RESEARCH.md).

Сергей передаёт харнесс v0 Коле; Коля с Димой подключают реальные SQL/RAG/hybrid-задачи и снимают baseline/скорость. Сергей с Вовой параллельно готовят GEPA/SFT-данные и проверяют тренировочный стек. Синтетическое SQL-демо проверяет интеграцию, а результаты на документных наборах относятся к RAG-направлению.

## Инструменты

| Инструмент | Вход | Результат |
|---|---|---|
| Поиск | Запрос к выбранному корпусу | Ранжированные документы или чанки с постоянными id и текстом |
| SQL | Запрос к доступной схеме | Типизированный результат либо понятная ошибка |
| Завершение | Свидетельства и, для режима ответа, ответ агента | Сохранённый результат эпизода для оценщика |

Сергей и Дима согласуют общий SQL-контракт, доступную схему, диалект и ограничения. SQL выполняется только для чтения, с ограничениями вычислений и результата. Эталоны скрыты от модели. Контракт версии 3 добавляет SQL и ответ к демо; finish(document_ids) остаётся интерфейсом retrieval-режима.

## Проверка качества

Retrieval оцениваем по qrels с фиксированной единицей документа/чанка. Accuracy ответа считаем отдельно по протоколу набора. Для SQL проверяем смысловой результат выполнения, задав правила типов, точности и порядка строк; успешное выполнение запроса само по себе не доказывает правильность ответа.

Смешанная задача требует связанных таблиц и документов и проверки необходимости обоих источников. Наличие SQL-ручки не доказывает готовность такого набора. Награда может сочетать программную проверку и LLM-судью; строгий RLVR не обязателен. Оценщики фиксируются и проверяются до масштабирования.
