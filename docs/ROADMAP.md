# Дорожная карта проекта

Актуализация от **2026-11-01**: три недельных спринта. Предлагаемый календарь — 02–08.11, 09–15.11 и 16–22.11. Подробный план для раздачи команде — [SPRINT_1.md](SPRINT_1.md). Тикеты ещё не созданы; [BACKLOG.md](BACKLOG.md) — черновик для согласования.

## Результат и принятые решения

Открытая среда **Text-to-SQL + RAG**, воспроизводимое сравнение **GEPA, SFT и RL**, релиз и статья. Агент ищет факты в документах, выполняет SQL и объединяет результаты. Оценка включает SQL-only, RAG-only и hybrid; отдельная задача не обязана требовать оба инструмента.

Сергей передаёт первую рабочую версию харнесса Коле. **Коля и Дима разворачивают бенчмарки и снимают исходные результаты; Сергей и Вова параллельно готовят данные GEPA/SFT.** Сергей сохраняет ответственность за харнесс, совместимость с обучением и последующие методы. Коля может начинать runner на сохранённых эпизодах до передачи харнесса; Дима — готовить данные и сервисы.

GEPA, SFT и RL обязательны. Матрица из исходного агента, GEPA, SFT, прямого RL и SFT → RL остаётся предложением для основного сравнения. Рост качества — проверяемая гипотеза; в статью входят фактические результаты и ограничения.

## Данные

| Направление | Кандидаты для обучения | Кандидаты для внешней оценки |
|---|---|---|
| SQL | PAUQ train, BIRD train-filtered | PAUQ dev, BIRD dev |
| RAG | HotpotQA train | Ранее выбранные BrowseComp-Plus, TRuST, SynthComp-Ru/En |
| Hybrid | HyDRA train после аудита; собственные задачи при необходимости | HyDRA dev, HybridDeepResearch; независимый дополнительный набор — HybridQA dev |

Это рабочий выбор источников, а не уже готовые адаптеры и корпуса. Вова и Дима сначала проверяют файлы, БД, тексты, оценщики, лицензии и пересечения. FDABench — резерв после проверки доступа и подходящего SQL + текст среза. Окончательный состав панели фиксируем по аудиту, без выбора наборов по полученным метрикам.

Для оптимизации выделяем внутренний dev из разрешённых train-источников. Внешние вопросы, ответы и производные траектории исключены из обучения и GEPA. Предложение первого train-пилота — **300 задач: по 100 каждого типа**, плюс отдельный внутренний dev. Размер большого набора и пропорции смеси определяем после проверки качества, длины и стоимости траекторий; прежние 30/30/40 и около 3 тыс. задач не являются согласованными квотами. Протокол — в [EXPERIMENTS.md](EXPERIMENTS.md), источники — в [HYBRID_RESEARCH.md](HYBRID_RESEARCH.md).

## Передача харнесса Коле и Диме

Целевая точка передачи v0 — **03–04.11**, не конец первой недели. Передаём проверяемый интерфейс, не дожидаясь всех оптимизаций:

- единый запуск эпизода с конфигом модели, задачи и инструментов; рабочие SQL, поиск и завершение;
- воспроизводимые примеры SQL, RAG и hybrid; эталоны получает оценщик, а не модель;
- траекторию, ответ, tool errors, причину остановки, токены и времена; неизвестные показатели отмечены явно;
- пакетный запуск с изоляцией состояния, ограниченной параллельностью и корректной отменой;
- версию формата, инструкцию запуска, примеры подключения сервисов Димы и оценщиков Вовы.

Синтетические fixtures позволяют начать интеграцию. Первый замер качества требует реальных задач, источников и оценщика. После передачи Сергей исправляет блокеры и согласует изменения интерфейса; Коля владеет экспериментальным runner, возобновлением, MLflow и отчётами.

## Два параллельных потока первого спринта

| Поток | Ведущие | Результат к концу недели |
|---|---|---|
| Бенчмарки и скорость | **Коля + Дима**, Вова помогает с метриками | Пилотные задачи трёх типов проходят через реальные сервисы. Есть качество, покрытие, ошибки, p50/p95 задержки, завершённые эпизоды/мин и стоимость при записанной параллельности |
| Данные GEPA/SFT | **Сергей + Вова**, Дима предоставляет источники | Аудит и split-манифест пилота, задачи и feedback для GEPA, первые проверенные траектории учителя для SFT, стоимость и причины отбраковки |

Начинаем с разрешённого технического/train/dev-набора для отладки. Исходный результат на внешней панели можно снять раньше обученных вариантов **после фиксации его конфигурации и оценочного протокола**; по нему не подбираем промпт, данные, judge или checkpoint.

Скорость измеряем на одном фиксированном наборе SQL/RAG/hybrid после прогрева. Отдельно показываем модель, инструменты и overhead; быстрые ошибочные эпизоды не считаем успехом. Численный throughput задаём после пилота и расчёта нужного объёма GEPA, генерации учителя и RL.

## Зависимости обучения

**GEPA:** рабочий харнесс + train-пилот + feedback + внутренний dev → оптимизация промпта → фиксация P*.

**SFT:** инструменты + разделённые train-задачи + сильный учитель + проверка траекторий → обучение → dev-выбор. Генерация учителя идёт **параллельно GEPA**, её начало не зависит от P*. Финальный SFT использует зафиксированные train, формат и целевой промпт; примеры сериализуются под chat template обучаемой модели.

**RL:** совместимый тренер + train-задачи + reward + новые роллауты текущей политики → обновления весов → dev-выбор. Проверку реального обновления параметров начинаем в первой неделе. RL после SFT зависит от SFT-чекпоинта; прямой RL — нет. Для двух запусков фиксируем один пул задач и reward, отдельно учитываем бюджеты.

Награда может сочетать программную проверку и LLM-судью: строгий RLVR не обязателен. Успешные учительские траектории нужны SFT; RL-пул не ограничиваем вопросами, прошедшими SFT-фильтр.

## Ресурсы и ограничения

В первом спринте измеряем цену роллаута, учителя, GEPA и обновления весов. По пилоту выбираем объёмы, параллельность и бюджеты запусков. Исторические GPU-часы и расходы не считаются доступным лимитом; платные запуски требуют отдельно разрешённого бюджета.

При нехватке времени уменьшаем объёмы, дополнительные модели, повторы и число кандидатов. Удаление GEPA, SFT или RL меняет согласованный scope. Состав панели, учителя, ресурсы и тренировочный стек фиксируем до основных запусков. Issue создаём после согласования плана.
