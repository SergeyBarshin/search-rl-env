# Память самообучающегося харнесса

Разрабатываем собственный GEPA-like оптимизатор для собственного Text-to-SQL + RAG-харнесса. Между пользовательскими запросами он анализирует завершённые траектории и отбирает версии инструкций. Сначала меняются промпты, затем добавляется создание и редактирование текстовых skills. Веса модели фиксированы. [Архитектура](RUNTIME_OPTIMIZER.md).

**Целевая архитектура от 17 ноября 2026 года.** Память позволяет SQL + RAG-агенту использовать опыт прошлых сессий, сохранять существенные сведения и исправления и поддерживать повторно используемые процедуры. Она определяет вариант memory-only; план реализации и оценки задан в [PAPER_PLAN.md](PAPER_PLAN.md) и [EXPERIMENTS.md](EXPERIMENTS.md).

## Ориентир Hermes и наша постановка

В Hermes постоянные записи подмешиваются в контекст сессии, история доступна через поиск, а skills загружаются по необходимости. Отдельный curator обслуживает библиотеку созданных агентом навыков. Источники: [Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory), [Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills), [Curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator).

У нас эти механизмы образуют единый Memory Manager для SQL + RAG. Персональный профиль пользователя добавляется только в сценариях, где он нужен; основной контекст — работа с БД, документами и историей решений. Это проект собственной архитектуры, а не утверждение о полном воспроизведении Hermes.

## Состав памяти

| Часть | Что хранит | Как используется |
|---|---|---|
| История сессий и эпизодов | Вопросы, действия, наблюдения, ответы и разрешённая обратная связь | Поиск конкретного прошлого опыта по запросу |
| Долговременные записи | Существенные сведения о мире, проверенные соглашения, исправления и краткие выводы | Ограниченный по токенам блок при начале сессии; выбор по области действия |
| Процедурная память | Skills: способы решения, условия применения и типичные ошибки | Краткий каталог и загрузка подходящей процедуры по необходимости |
| Политика обслуживания | Правила добавления, уточнения, объединения, разрешения противоречий и архивирования | Обновление памяти после завершённого использования |

Рабочая история текущего эпизода остаётся контекстом модели. Память переносит полезный опыт через границы эпизодов и перезапусков. Корпус RAG содержит исходные документы задачи и не смешивается с поисковым индексом истории агента.

## Цикл использования

1. Открыть сессию с `memory_snapshot_id`, доступной областью мира и бюджетом памяти.
2. Сформировать компактный начальный контекст. В ходе решения агент может искать прошлые эпизоды и читать подходящие навыки через согласованный интерфейс.
3. Выполнить SQL/search и сформировать ответ. Сохранить использованные записи и их версии в траектории.
4. В потоковом эксперименте зафиксировать независимую оценку первой попытки и затем выдать разрешённый feedback.
5. Записать завершённый разрешённый эпизод в историю; подготовить изменения записей и процедур.
6. Объединить дубли, обработать исправления и устаревшие сведения, сохранить решение по каждому изменению и опубликовать следующий снимок.

Память обновляется на границе завершённых эпизодов или пакетов. Параллельный пакет читает один снимок; публикация идёт в заданном порядке, а не по случайной скорости ответов. Запланированные изменения не переписывают контекст уже работающего эпизода.

## Чтение и запись

Планируемые операции — `prepare_context`, `search_history`, `read_memory`, `propose_update`, `consolidate`, `snapshot` и `restore`. Публичные инструменты и формат метаданных согласуются с владельцами в [CONTRACTS.md](CONTRACTS.md) до реализации. Эти имена не являются существующей CLI/API.

У каждой записи есть id, тип, версия, область действия, происхождение, подтверждающие эпизоды, статус и связь с прежней записью. Сохраняются операции add/update/merge/archive и причины изменений. Архивирование не уничтожает журнал происхождения; восстановление возвращает точное состояние.

Для памяти задаются отдельные лимиты: начальные записи, результаты поиска истории, каталог и содержимое навыков, стоимость извлечения и обслуживания. Лимиты являются частью конфигурации. Изменение памяти не должно незаметно увеличивать контекст между сравниваемыми вариантами.

Качество нельзя определять только тем, что анализатор назвал запись полезной. Проверку пользы выполняет независимая оценка следующих решений. Дополнительный отбор обновлений по метрике допустим как исследуемый механизм, но не является единственным определением памяти или обязательной формой каждого использования.

## Области действия и актуальность

Память изолируется по эксперименту, варианту метода и независимому запуску. Внутри выделяются общие процедуры и записи, привязанные к миру, версии схемы, корпуса или пользовательского контекста. Факт о старой версии данных не считается автоматически действующим после её изменения.

Например, исправление трактовки поля конкретной таблицы сохраняется с ревизией схемы; процедура проверки кардинальности JOIN может иметь более широкую область действия. Переход от локального наблюдения к общей записи фиксируется и оценивается, а не происходит только из-за формулировки анализатора.

Противоречащие записи связываются с источниками. Новая запись не заменяет прежнюю без причины и версии. Сроки устаревания и критерии архивирования задаются заранее; в экспериментах используется воспроизводимый порядок событий вместо случайного фонового таймера.

## Контракт эпизода

Харнесс предоставляет публичный журнал эпизода и подключает начальный контекст и операции памяти. Вызовы чтения/записи, выбранные записи, их версии, наблюдения и затраты связываются с Trace. Новые поля и инструменты не считаются реализованными из этого описания.

Для поиска истории строится разрешённое представление Trace: публичные сообщения, вызовы, наблюдения и объявленный feedback. Приватные поля TaskData, reference_answer, reference_document_ids и gold SQL не индексируются напрямую. Полная Trace остаётся отдельным артефактом аудита; разрешённое пользовательское исправление передаётся в память через событие feedback по протоколу.

Результаты памяти являются контекстом/наблюдениями, а не сгенерированными целевыми токенами модели. Оптимизатор памяти не изменяет оценщик, инструменты, gold или правила бюджета.

## Два режима оценки памяти

**Закрытая оценка:** снимок доступной памяти неизменяем. Новые тестовые траектории хранятся только для аудита и не доступны последующим тестовым вопросам. Метрики использования памяти тоже не изменяют её ранжирование или обслуживание в этом режиме.

**Поток использования:** текущая оценка фиксируется до feedback. Следующий снимок может использовать текущий завершённый опыт и разрешённые исправления, но не будущие задачи/эталоны. Исправление не меняет уже сохранённый результат первой попытки. Политика обратной связи одинакова у сравниваемых вариантов.

## Первая техническая приёмка

- Сессия записала опыт; новая сессия и перезапущенный процесс действительно находят нужную историю, запись или процедуру.
- Исправление обновило запись с происхождением; старый снимок доступен для воспроизведения.
- Чужой мир, вариант эксперимента и закрытые тестовые эпизоды не доступны через поиск памяти.
- Смена ревизии источника обрабатывает локальные сведения по объявленной политике.
- Отмена и resume не создают повторных публикаций и не теряют учёт расходов.
- Память и инструменты работают в целевом runtime; сравнение с отключённой памятью воспроизводимо на моках.

Владелец логики памяти — Сергей. Дима поддерживает хранение и индексы по согласованному контракту; Коля связывает снимки с прогонами и возобновлением; Вова задаёт сценарии исправлений, эталоны и независимые проверки.
