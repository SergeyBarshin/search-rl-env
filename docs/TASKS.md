# Зоны ответственности и материалы по runtime-адаптации

Текущая последовательность работ по текстовому baseline описана в [ROADMAP.md](ROADMAP.md#ближайший-замер) и [EXPERIMENTS.md](EXPERIMENTS.md#план-замеров-на-публичных-наборах). Ниже сохранены проектные зоны ответственности и материалы по компонентам.

## Ближайшие задачи

**Коля — перенести логи прогонов и версии бенчмарков в Google Cloud Storage с S3-совместимым доступом.** Для приёмки взять один завершённый прогон и один набор задач, загрузить артефакты, записать пути и контрольные суммы в manifest. Из чистой папки восстановить набор и пересобрать отчёт по логам. Приватные эталоны хранить отдельно от данных, доступных агенту.

**Вова — подготовить две исполняемые задачи, в каждой нужны SQL и поиск по документам.** В первой документ задаёт условие для запроса к БД, во второй SQL находит сущность, о которой нужно найти факт в документах. Передать вопрос, небольшой снимок БД и корпуса, приватный эталон, подтверждающие строки и фрагменты, правило проверки. Можно адаптировать другие бенчмарки, если лицензии вопросов, таблиц и текстов разрешают переработку и распространение в составе нашего набора. Для заимствований приложить источник, версию, лицензию и требуемую атрибуцию. Если права неясны, подготовить собственные данные.

Работы идут параллельно по согласованным форматам задачи, инструментов, ответа, оценки и артефакта запуска в [CONTRACTS.md](CONTRACTS.md). Интеграционные зависимости в backlog означают условия приёмки, а не запрет начать реализацию с fixtures.

Первый совместный результат: агент сам решает выбранную панель без gold SQL и памяти; команда получает таблицу качества, задержек, стоимости и ошибок. Моки и gold SQL replay проверяют инструменты, но не качество агента. На этом этапе история хранится только для аудита и не доступна агенту в последующих задачах.

## Приёмка и переход к памяти

BAS-02 принимается после BAS-01 и инженерных проверок, когда разобраны ошибки, таблица воспроизводится из артефактов и подтверждены источники. Фиксируются модель, prompts, версии, выборка, бюджеты и правила оценки. Размер панели и платный бюджет согласуются до запуска. Итоговый закрытый тест не используется для разработки.

Не требуется заранее заданный высокий процент правильных ответов. Требуются исправные инструменты/оценщик и достоверные измерения. Если причина ошибок — сломанный поиск или SQL, сначала исправляем её и обновляем baseline. Если для сравнения позже меняется общий харнесс, оба варианта измеряются на одинаковой новой версии.

HyDRA — кандидат гибридной панели, BIRD — SQL, HotpotQA — RAG. Не требуется сразу запускать все три полностью. Размеры, версии, источники и подвыборки явно записываются; собственный сокращённый запуск не называется официальным benchmark score. Для HyDRA отдельно определить доступность схем, evidence/hints и других полей: не передавать агенту приватные ответы/SQL из карточки.
