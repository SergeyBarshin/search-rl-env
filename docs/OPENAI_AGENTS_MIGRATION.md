# Переход на OpenAI Agents SDK

Цель этапа M0 — запустить собственный статический SQL + RAG-харнесс через Python-пакет `openai-agents` в чистом окружении без Verifiers. SDK исполняет цикл модели и инструментов. Проект владеет промптами, схемами SQL/search/finish, форматом эпизода, хранением трасс и независимым eval. Базовые замеры M1 снимаем после перехода.

## 1. Зафиксировать поведение прототипа — Сергей и Вова

Сохранить небольшие fixtures и ожидаемые результаты для retrieval и связанной задачи SQL + RAG. Включить команды примеров, порядок сообщений, аргументы инструментов, правила завершения, бюджетную остановку и формат ошибок. Зафиксировать контракт публичной функции run_episode и поля EpisodeResult, которые читают UI, batch-runner и отчёты. Вова указывает приватные эталоны и проверяет независимый пересчёт оценки из первого ответа.

Результат — набор входов и проверяемых ожиданий, которые можно воспроизвести после удаления старого исполнителя.

## 2. Проверить SDK и транспорт на одном эпизоде — Сергей

В изолированном окружении выбрать и закрепить совместимую с проектом версию SDK. Собрать минимальный Agent с версией промпта и тремя function tools. Использовать Runner и OpenAIChatCompletionsModel с настроенным AsyncOpenAI для совместимого endpoint. На локальной HTTP-заглушке воспроизвести реальные сообщения протокола, отключить автоматические повторы клиента и внешний экспорт tracing. Проверить фактические schemas, tool_call_id, порядок сообщений, usage, таймаут и количество обращений. Сверить поддержки нестандартной авторизации и параметров провайдера с существующим agent/client.py.

Критерий — три хода модели для скрипта search → sql → finish. После успешного finish ответ и ссылки выдаются сразу. Невалидный finish возвращает наблюдение об ошибке и допускает исправление в пределах бюджета. Проверить также пакет из нескольких tool calls с finish внутри. Если стандартная конфигурация SDK нарушает порядок действий, локализовать исправление в адаптере и повторить этот сценарий до интеграции. Реальную проверку выбранной модели через OpenRouter выполнять только при согласованном бюджете.

## 3. Подключить предметные инструменты и оценщик — Дима, Сергей и Вова

Дима выделяет исполнение SQL/search из привязанных к Verifiers environment/tools.py и hybrid_tools.py, переиспользует существующие backend-интерфейсы, read-only SQL, ограничения выдачи и снимки БД/корпуса. Сергей подключает инструменты к SDK и закрепляет за эпизодом версию инструкций и источников. Вова выносит расчёт метрики в независимый оценщик. Публичный журнал содержит вопрос, разрешённые действия и наблюдения, ответ, причину остановки и расходы. Эталоны доступны только оценщику.

Критерий — сквозной локальный пример с реальными тестовыми таблицами и документами, проверяемым ответом и ссылками. Проверить, что приватных полей нет в сообщениях модели и в публичном журнале для будущего replay.

## 4. Перевести обычные точки запуска — Коля и Сергей

За интерфейсами run_episode и RolloutRunner переключить исполнение на SDK. Обеспечить отдельное состояние на каждый эпизод, общий пул соединений, лимиты параллельности, отмену и корректное закрытие ресурсов. Проверить интерактивный пример, batch, UI и повторное чтение сохранённых результатов. При изменении схемы дать ей новую версию и сохранить чтение прежних JSON. Явно различать неизвестный usage и нулевой расход.

Критерий — одиночный запуск и batch на одинаковом fixture дают согласованные результаты. Отмена одного эпизода сохраняет результаты соседних. Повторный запуск отчёта по артефактам воспроизводит таблицу без вызовов модели.

## 5. Убрать старый runtime и принять переход — Сергей и Коля

После переключения потребителей удалить обязательный verifiers из pyproject.toml, старые пути interception/bridge и subprocess-программу в той части, где у них больше нет вызывающего кода. Заменить vf-eval в актуальных командах и CI. Перенести поведенческие проверки инструментов, ошибок и бюджетов. Исторические артефакты остаются читаемыми. Обновить установку и команды в README в той же поставке.

Приёмка из чистой установки — Verifiers отсутствует, CLI и batch выполняют локальные SQL + RAG-примеры, релевантные тесты и сборка отчёта проходят без ключей. Зафиксировать версии SDK/модели/промпта, набор задач и конфигурацию для M1. После этого на статическом агенте измеряем качество и расходы. Оптимизатор получает свой публичный контракт эпизода поверх уже измеренного харнесса.
