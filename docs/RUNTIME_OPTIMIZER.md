# Архитектура runtime-оптимизатора

Этап M0 подробно описан в [плане перехода на OpenAI Agents SDK](OPENAI_AGENTS_MIGRATION.md).

Разрабатываем собственный GEPA-like оптимизатор для собственного Text-to-SQL + RAG-харнесса. Между пользовательскими запросами он анализирует завершённые траектории и отбирает версии инструкций. Сначала меняются промпты, затем добавляется создание и редактирование текстовых skills. Веса модели фиксированы.

## Граница собственного харнесса

Статический харнесс использует OpenAI Agents SDK для запуска модели и инструментов. Публичный EpisodeResult служит входом replay. Оценщик автономно читает сохранённый ответ. [Миграция и приёмка](OPENAI_AGENTS_MIGRATION.md).

| Компонент | Ответственность |
|---|---|
| Харнесс | Закрепить версию промпта, skills, схему инструментов и снимки БД/корпуса на эпизод |
| Runtime | Исполнить вызовы модели и инструментов, завершить эпизод на finish, учитывать лимиты, ошибки и отмену |
| Транспорт | Передать messages и tools в Chat Completions endpoint, учесть число попыток, таймаут и доступный usage |
| Журнал | Сохранить первую попытку, публичные действия, версии и расходы |
| Оценщик | Сопоставить ответ с закрытым эталоном и записать результат в исследовательский журнал |

## Приёмка статического исполнителя

Запустить чистое окружение без пакета verifiers. В SDK передать SQL/search/finish как function tools и зафиксировать инструкции на весь эпизод. Скриптовый провайдер ведёт запрос через поиск документа, SQL-запрос и finish. Проверить фактические messages и tool call ID, итоговый ответ, отсутствие дополнительного хода после finish, usage, ошибку инструмента, таймаут и отмену. Проверить отдельно, что обычный запуск и replay получают один публичный формат и что эталон скрыт от модели и оптимизатора. Схемы инструментов, адаптеры источников и fixtures переиспользовать после проверки их импортов в чистом окружении. [Документация SDK](https://openai.github.io/openai-agents-python/).

Исполнитель зафиксирован на OpenAI Agents SDK. Текстовый режим переносит рабочие свидетельства между раундами одного эпизода. Ближайшие прогоны фиксируют исходный Recall@10 перед проверкой адаптации между запросами. [Методика](EXPERIMENTS.md#план-замеров-на-публичных-наборах).

## Обновление между запросами

1. Разделяем уже завершённые запросы на discovery и replay по семействам. Анализатор читает discovery, формулирует проблему и указывает эпизоды, где она наблюдалась. Например, агент потерял фильтр по дате при переходе от SQL к поиску документов.
2. Генератор предлагает ограниченное число альтернатив для одного именованного блока промпта, например инструкции переноса ограничений между инструментами. Каждое предложение содержит родительскую версию, изменение и обоснование. Текущая версия входит в сравнение.
3. Runner заново исполняет текущую версию и кандидатов на одних replay-запросах, снимках данных и лимитах. Критик с фиксированными моделью и инструкцией видит обезличенные пары ответов, публичные действия и свидетельства. Порядок сторон рандомизируется. Допускается ничья.
4. До запуска фиксируем лимит кандидатов, правило ничьих и порог принятия. Рабочий вариант для пилота считает победу за 1, ничью за 0,5 и выбирает кандидата с лучшим средним выше заданного порога при соблюдении лимитов и контрактов инструментов. При равенстве лучших результатов или недостатке свидетельств сохраняется текущая версия. Порог настраивается на разработке.
5. Реестр атомарно публикует выбранную версию на границе эпизодов. Записывает родителя, идентификаторы discovery/replay, мнения критика, решение и затраты, включая отклонённых кандидатов. Повтор после сбоя использует идентификатор события. Откат восстанавливает конкретный снимок. Закрытая оценка не управляет публикацией или откатом.

## Варианты и расширения

V1 периодически оптимизирует промпты выбора SQL/search, отбора контекста и завершения ответа. Решающий агент получает активную версию инструкций. Поиск старых эпизодов доступен оптимизатору. В memory-only базовые инструкции закреплены, агент извлекает историю, заметки и процедуры из собственной памяти. [Архитектура памяти](MEMORY_CORE.md).

На следующем шаге тот же генератор и селектор могут создавать или редактировать версионированные текстовые skills с условиями вызова. В отдельном опыте запуск по расписанию заменяется запуском по повторяющемуся сигналу из нескольких эпизодов. Меняем по одному фактору. Инструменты, права, исполнитель и критик фиксированы. Эти компоненты и интерфейсы запланированы. [Протокол экспериментов](EXPERIMENTS.md).
