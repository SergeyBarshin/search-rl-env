## 1. Питч проекта — 2 минуты

> Мы делаем открытую среду для обучения агента, который отвечает на вопросы по базам данных и документам. Агент сам решает, когда выполнить SQL, когда искать текст и как объединить результаты в ответ.
>
> Например: «Каким заказам положена компенсация?» Условия компенсации находятся в регламенте, а статусы, суммы и задержки заказов — в базе. Для правильного ответа нужно связать оба источника.
>
> В среде можно запускать разные модели, собирать траектории, оценивать ответы и обучать агента. На одной целевой Qwen сравним исходный агент, GEPA — оптимизацию промпта, SFT — обучение на проверенных решениях сильного учителя, и RL — обучение по награде за собственные попытки.
>
> За три недели хотим получить работающую открытую среду, воспроизводимые эксперименты и статью: какие методы изменили качество, сколько это стоило и с какой скоростью можно собирать роллауты. Улучшение качества проверяем на отложенных задачах. В результаты включаем фактически измеренный эффект каждого метода.

## 2. Что именно строим — 4 минуты

| Компонент | Что делает | Основной владелец |
|---|---|---|
| Агент и харнесс | Цикл модели и инструментов, контекст, завершение, траектория, подключение обучения | Сергей |
| Инструменты среды | SQL, доступная схема, поиск по документам, версии источников, ошибки | Дима |
| Инфраструктура экспериментов | Пакетные запуски, возобновление, оценка сохранённых эпизодов, MLflow и отчёты | Коля |
| Данные и оценка | Вопросы, эталоны, сплиты, метрики, judge и контроль качества | Вова |

Общий путь: задача → харнесс → модель → SQL/search → ответ и траектория → оценщик → отчёт. Эталон получает оценщик; модель решает задачу по разрешённым источникам. Порядок и количество действий выбирает агент.

### Что уже есть

- Python-пакет, агентный цикл на Verifiers, API-клиенты модели и бесплатные моки.
- Retrieval-пример и связанное SQL + RAG демо с SQLite.
- `run_episode`, пакетный `RolloutRunner`, сохранение результатов, профилирование и автономные тесты.
- [Инструкция передачи харнесса](HARNESS_HANDOFF.md), [контракты](CONTRACTS.md) и [описание поиска](RAG_SEARCH.md).

### Что продолжаем делать

Подключаем реальные БД и поиск, общий формат ответа, выбор нужной БД для задачи, реальные benchmark-оценщики и экспериментальный runner. В существующем retrieval-демо финал — id документов; в hybrid-демо ответ — список id заказов. Общий SQL/RAG-бенчмарк требует согласованного расширения. GEPA, SFT-экспорт и реальное обучение модели ещё предстоят.

## 3. Данные и измеримый результат — 4 минуты

Оцениваем три навыка отдельно: SQL-only, RAG-only и hybrid. Не каждый вопрос обязан требовать оба инструмента.

| Тип задач | Рабочие источники train | Внешняя оценка |
|---|---|---|
| SQL | PAUQ train, BIRD train-filtered | PAUQ dev, BIRD dev |
| RAG | HotpotQA train | BrowseComp-Plus, TRuST, SynthComp-Ru/En |
| Hybrid | HyDRA train после аудита; собственные задачи при необходимости | Кандидаты: HyDRA dev, HybridDeepResearch; дополнительно HybridQA dev |

Новые источники и состав панели подтверждаем после проверки файлов, БД, корпусов, оценщиков и лицензий. Исследование — в [HYBRID_RESEARCH.md](HYBRID_RESEARCH.md).

До генерации отделяем внутренний dev от train, проверяем переводы/производные вопросы и пересечения источников. Внешние оценочные вопросы и ответы не используются для GEPA, обучения или выбора checkpoint. Предложение первого train-пилота — 300 задач, по 100 каждого типа, плюс отдельный dev; объём уточняем после первых проверок.

Из общего пула получаются три продукта:

- **GEPA:** задачи, инструменты и feedback; целевая модель пробует решения, оптимизатор меняет промпт.
- **SFT:** успешные проверенные траектории сильного учителя через наш харнесс.
- **RL:** задачи, среда и награда; текущая модель собирает новые попытки и обновляет веса.

Генерация учителя идёт параллельно GEPA. Награда может сочетать программные проверки и LLM-судью; строгий RLVR не обязателен. Судью проверяем на ручной выборке.

Результат сравнения: отдельные метрики каждого набора, покрытие и ошибки, скорость и стоимость. Предлагаемая матрица — исходный агент, GEPA, SFT, прямой RL и SFT → RL. GEPA/SFT/RL обязательны; бюджеты и пять строк сравнения фиксируем перед основными запусками.

## 6. Как продолжать разработку — 5 минут

Репозиторий: [SergeyBarshin/search-rl-env](https://github.com/SergeyBarshin/search-rl-env). Сергей подтверждает команде ветку/commit передачи; установка — по [README](../README.md). Для нового клона:

```bash
git clone https://github.com/SergeyBarshin/search-rl-env.git
cd search-rl-env
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m pytest -q
```

Показать бесплатный hybrid-пример и сохранённую траекторию:

```bash
python -u examples/run_episode.py --model mock --scenario sql_rag --verbose \
  --output runs/kickoff/hybrid/episode.json
python -m search_rl_env.profiling runs/kickoff/hybrid/episode.json
```

Ожидаемый ответ мока — `ORD-101`, `ORD-105`, источник `policy-001`. Это проверка интеграции на синтетических данных. Полные инструкции подключения своих задач и сервисов — в [HARNESS_HANDOFF.md](HARNESS_HANDOFF.md).

Порядок работы после созвона:

1. Подтвердить задачи из [BACKLOG.md](BACKLOG.md); после согласования Сергей заведёт тикеты с одним ответственным и критерием готовности.
2. Работать короткими ветками от актуального `main`: например, `feat/sql-backend`, `feat/evaluation-runner`, `feat/dataset-pilot`. Для раннего обсуждения интерфейса открывать draft PR.
3. Сначала передать соседнему компоненту маленький проверяемый пример входа/выхода. Изменение общего формата записать в [CONTRACTS.md](CONTRACTS.md) и согласовать с его потребителями.
4. В PR указать задачу, результат и проверку. Перед слиянием — ревью; первые технические PR Коли смотрит Сергей или Дима. Общие правила — в [CONTRIBUTING.md](../CONTRIBUTING.md).
5. Ежедневно коротко писать: готовый артефакт, следующий шаг, блокер. Блокеры интеграции поднимать сразу.

Ключи хранятся локально, большие данные и артефакты — вне Git. Платные API/GPU-прогоны выполняются в согласованном с Сергеем бюджете; доступы и ресурсы подтверждаем на встрече. В стандартных тестах используются моки.
