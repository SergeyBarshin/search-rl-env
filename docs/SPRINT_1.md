# Спринт 1: харнесс, baseline и пилот данных

**Срок: 2–8 ноября 2026.** Цель недели — рабочая среда SQL + RAG и два независимых потока: **Коля + Дима снимают исходное качество и скорость; Сергей + Вова готовят данные GEPA/SFT**. Код и частичные интеграции уже есть: сначала сверяем готовность, затем закрываем недостающее.

## Что показываем в конце недели

1. Реальная hybrid-задача проходит через харнесс, SQL и поиск; ответ, действия и оценки сохранены.
2. На фиксированном внутреннем пилоте SQL/RAG/hybrid есть исходные метрики, ошибки, задержки и стоимость.
3. Есть разделённые train/internal dev, первые проверенные SFT-траектории и выполненный GEPA-пилот.
4. Проверен путь к обучению Qwen: формат/маски, техническое обновление весов и сохранение/загрузка. Сбор API-траекторий сам по себе это не проверяет.

Основные SFT/RL-запуски остаются во втором спринте. Даты ниже — рабочие контрольные точки; объёмы уточняем по качеству и стоимости пилота.

## Сергей — харнесс, генерация траекторий, модели

**До 3–4 ноября: передать v0 Коле и Диме** (`ORG-01`, `AG-01`).

- Зафиксировать вызов эпизода и пакета, конфиги модели/инструментов, формат задачи и результата.
- Проверить SQL, поиск, финальный ответ, сохранение tool calls и наблюдений, ошибки, завершение/отмену и изоляцию эпизодов.
- Дать воспроизводимые примеры SQL/RAG/hybrid и инструкцию. Для начала интеграции подходят fixtures; gold отделён от входа модели.
- С Димой подключить реальные SQL/search, с Колей проверить чтение результата (`AG-03`, до 5 ноября). После передачи поддерживать интерфейс и исправлять блокеры.

**Остаток недели — вместе с Вовой** (`TR-04`, `TR-05`).

- Собрать конвейер: train-задача → сильный учитель через тот же харнесс → оценка → принятая/отклонённая траектория с причиной.
- Проверить экспорт под chat template Qwen и маски: результаты инструментов — контекст, assistant-действия/ответы — цели SFT.
- Подключить GEPA к задачам и feedback, выполнить небольшой пилот и сохранить кандидаты/расходы. Генерация учителя не ждёт окончания GEPA.
- С начала недели проверить ресурсы и тренировочный стек, затем агентный цикл с обучаемыми весами (`ORG-02`, `AG-02`). Результат — реальное техническое обновление параметров, сохранение и загрузка; при отсутствии ресурсов явно записать блокер.

**Передаёт:** Коле — харнесс и примеры; Вове — траектории и экспорт; команде — конфиги модели, результат проверки тренера, GEPA-пилот.

## Дима — реальные источники, SQL и поиск

**2–4 ноября** (`DB-01`): с Вовой проверить наличие вопросов, БД, текстов, связей сущностей и лицензий. Для первого train-пилота рабочие источники — BIRD/PAUQ, HotpotQA, HyDRA; начинаем с минимального проверенного пути каждого типа.

**До 5 ноября** (`DB-02`, `DB-04`):

- Поднять SQL только для чтения: нужная БД и схема по задаче, ограничения времени/результата, понятные ошибки.
- Поднять поиск по нужному корпусу: постоянные id, тексты, ревизии; чтение по id, если требуется протоколом.
- Соединить сервисы с харнессом Сергея, проверить эталонный SQL и наличие нужных документов.

**6–7 ноября** (`DB-03`): с Колей провести параллельный прогон, проверить нагрузку/таймауты и снять времена инструментов. Зафиксировать снимки/индексы, параметры поиска и инструкцию запуска для следующих методов.

**Передаёт:** работающие SQL/search, конфиги источников и маппинг id. Содержание задач и сплиты определяет Вова.

## Коля — runner, baseline и скорость

**Начать сразу на сохранённых эпизодах**, не ждать всех сервисов (`EV-01`, `EV-02`, до 4–5 ноября).

- Подключить оценщики Вовы; получить таблицу по задачам с ошибками, пропусками и покрытием.
- Подключить публичный пакетный интерфейс харнесса. Добавить конфиги набора/модели/промпта, возобновление по id, учёт попыток и сохранение артефактов/MLflow.
- С Димой подключить реальные источники; Вова предоставляет формат задач, эталоны и метрики.

**До 7 ноября** (`EV-03`, `EV-06`): снять исходный Qwen/P0 на фиксированном внутреннем пилоте SQL/RAG/hybrid. Отдельно показать качество ответа, корректно завершённые эпизоды, ошибки и стоимость. Для скорости — эпизоды/мин, p50/p95, параллельность и времена модели/инструментов/харнесса после прогрева. API и тренировочный инференс отмечать отдельно.

**До 8 ноября** (`EV-04`): тот же runner принимает GEPA-кандидат или checkpoint и оценивает внутренний dev. Внешний baseline допустим после фиксации его конфигурации и протокола; внешние результаты не используются для подбора.

**Передаёт:** команду воспроизводимого запуска, сохранённые эпизоды и отчёт исходного качества/скорости. Целевой throughput рассчитываем по этим измерениям и нужному объёму обучения.

## Вова — задачи, split, оценщики и фильтры

**2 ноября** (`BM-01`): реестр источников с ролью train/dev/eval, ревизиями, лицензиями, нужными БД/корпусами и оценщиками. С Димой проверить готовность HyDRA; с Сергеем — происхождение данных и пересечения.

**До 4–5 ноября** (`BM-02`, `BM-03`):

- Подготовить контрольный пакет с разобранными SQL/RAG/hybrid-задачами; ориентир первого пакета — по 10 каждого типа.
- Выделить internal dev до генерации. Сгруппировать переводы и производные задачи; проверить BIRD↔HyDRA и Spider↔PAUQ.
- Проверить gold SQL, документы, неоднозначность и содержательную необходимость двух источников у hybrid.
- Передать Коле оценщики и fixtures правильных/ошибочных ответов. Для judge сопоставить оценки с ручной выборкой; строгий RLVR не обязателен.

**5–8 ноября, с Сергеем:** проверить первые траектории учителя, зафиксировать фильтры SFT и причины отбраковки, подготовить задачи/feedback для GEPA. Ориентир расширенного train-пилота — по 100 задач каждого типа плюс отдельный dev; это предложение объёма, не основание принимать некачественные задачи.

По внешней панели (`BM-05`) зафиксировать доступность, протоколы, маппинг id и минимальные адаптеры/fixtures: PAUQ/BIRD для SQL, ранее выбранные RAG-наборы, кандидаты HyDRA/HybridDeepResearch и дополнительно HybridQA для hybrid. Основной внешний прогон обученных вариантов — в третьем спринте.

**Передаёт:** train/dev-манифест, эталоны/свидетельства, оценщики, аудит первых SFT-траекторий и список проблем данных.

## Общие правила недели

- Полноту источников проверяем рано. Если БД/корпус HyDRA недоступны, фиксируем блокер и используем разобранные собственные hybrid-задачи для интеграции. Их результаты подписываем как собственный пилот. Ограниченный индекс — отдельный протокол, не официальный результат полного бенчмарка.
- Внешние оценочные вопросы, gold и производные траектории не попадают в GEPA/SFT/RL или подбор judge. Внутренний dev используется для выбора вариантов.
- Записываем ревизии данных/модели/промпта/оценщика, бюджеты, параллельность, ошибки и расходы. Платные API/GPU-запуски — в отдельно разрешённом бюджете.
- В течение недели каждый отмечает готовый артефакт, следующий шаг и блокер. Изменения общего интерфейса согласуем с его потребителями.
