# Проверка адаптации на пользовательском потоке

В основном эксперименте адаптации доступны запрос, ответ, публичные вызовы и результаты инструментов, ошибки и суждения внутреннего критика. Эталонный SQL, ответы, метки документов, benchmark reward и оценки исследователей доступны только независимому оценщику. Исправления с правильным ответом допустимы в отдельном явно обозначенном эксперименте.

## Поток и закрытый тест

До запуска разделяем семейства вопросов и миров на разработку, поток и независимый финальный тест. Для каждой конфигурации воспроизводим один порядок запросов и границы сессий, одинаковые модель, SQL/search, снимки источников, лимиты решения и общий доступный бюджет адаптации. Каждый вариант получает собственные траектории. В начале новой сессии сбрасываем рабочий контекст.

Текущая версия отвечает один раз. Оценщик записывает результат в закрытый журнал. Только после ответа публичный эпизод становится доступен адаптации для последующих задач. Discovery и replay содержат разные прошлые семейства, replay ротируется с лимитом повторных проверок. На финальном тесте замораживаем память, промпты и skills. Потоковая подвыборка открытого набора имеет собственный протокол оценки.

## Открытая панель

| Постановка | Кандидаты | Что проверить |
|---|---|---|
| Hybrid SQL + RAG | HyDRA; дополнительно HybridDeepResearch/HybridQA | БД, корпус, связь сущностей, достаточные свидетельства, ответ и независимый оценщик |
| SQL | BIRD/PAUQ | Execution-проверка, диалект, ревизии БД и производные задачи |
| RAG | HotpotQA; внешние BrowseComp-Plus, TRuST, SynthComp RU/EN | Источники, qrels, единица документа/чанка, метрика ответа и права использования |

Все источники являются кандидатами до аудита; реестр — [HYBRID_RESEARCH.md](HYBRID_RESEARCH.md). Проверяем BIRD↔HyDRA и Spider↔PAUQ. Оценочные preview, запрещённые для обучения/адаптации, используются только в закрытой оценке. Одна задача с gold SQL из [HYDRA_PILOT.md](HYDRA_PILOT.md) проверяет инструменты и не заменяет самостоятельный benchmark-прогон агента.

## Собственный поток

Готовим задачи SQL → поиск, поиск → SQL и объединение независимых источников. Включаем повторяющуюся ситуацию с новыми сущностями, новую схему, смену документа и возврат к старому семейству. Точный повтор помечаем отдельно. Сравниваем стационарный поток и смену распределения на парных порядках. Планируем несколько порядков/seed и группируем неопределённость по потокам или мирам.

## Сравнения

| Вариант | Что переносится между сессиями |
|---|---|
| Static | Фиксированный исходный промпт |
| Memory-only | Извлекаемые записи, эпизоды и процедуры в духе Hermes |
| Prompt-evolution | Опубликованная версия промпта после внутреннего replay |
| Prompt + skills | Та же политика отбора с разрешёнными изменениями текстовых процедур |

Сначала сравниваем первые три варианта. Затем отдельно проверяем skills при том же расписании и запуск по повторяющимся сигналам при том же пространстве кандидатов. Считаем расходы анализа всех эпизодов, в том числе когда обновление пропущено.

## Результаты

Для каждого варианта показываем качество первой попытки по типам задач, накопленную парную разницу со static, регрессии, полную стоимость и задержку. Сохраняем версии модели, данных, промптов и skills, seed, расходы critic/replay, события принятия/отклонения и снимки памяти. Локальный manifest достаточен для пилота, целевой трекинг — MLflow.

Для проверки критика независимо прогоняем родителя и принятую версию на одинаковых следующих задачах в исследовательском режиме. Сопоставляем его предпочтение с изменением внешней метрики, включая вредные обновления. Эта диагностика скрыта от оптимизатора, её расходы показываем отдельно. Размеры, бюджет, пороги, оценщики и повторы фиксируем до итоговых прогонов.
