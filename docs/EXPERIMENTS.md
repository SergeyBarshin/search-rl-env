# Проверка адаптации на пользовательском потоке

В основном эксперименте адаптации доступны запрос, ответ, публичные вызовы и результаты инструментов, ошибки и суждения внутреннего критика. Эталонный SQL, ответы, метки документов, benchmark reward и оценки исследователей доступны только независимому оценщику. Исправления с правильным ответом допустимы в отдельном явно обозначенном эксперименте.

## Поток и закрытый тест

До запуска разделяем семейства вопросов и миров на разработку, поток и независимый финальный тест. Для каждой конфигурации воспроизводим один порядок запросов и границы сессий, одинаковые модель, SQL/search, снимки источников, лимиты решения и общий доступный бюджет адаптации. Каждый вариант получает собственные траектории. В начале новой сессии сбрасываем рабочий контекст.

Текущая версия отвечает один раз. Оценщик записывает результат в закрытый журнал. Только после ответа публичный эпизод становится доступен адаптации для последующих задач. Discovery и replay содержат разные прошлые семейства, replay ротируется с лимитом повторных проверок. На финальном тесте замораживаем память, промпты и skills. Потоковая подвыборка открытого набора имеет собственный протокол оценки.

## Открытая панель

| Постановка | Кандидаты | Что проверить |
|---|---|---|
| Hybrid SQL + RAG | HyDRA; дополнительно HybridDeepResearch/HybridQA | БД, корпус, связь сущностей, достаточные свидетельства, ответ и независимый оценщик |
| SQL | BIRD/PAUQ | Execution-проверка, диалект, ревизии БД и производные задачи |
| RAG | HotpotQA; внешние BrowseComp-Plus, TRuST, SynthComp RU/EN | Источники, qrels, единица документа/чанка, метрика ответа и права использования |

Все источники являются кандидатами до аудита; реестр — [HYBRID_RESEARCH.md](HYBRID_RESEARCH.md). Проверяем BIRD↔HyDRA и Spider↔PAUQ. Оценочные preview, запрещённые для обучения/адаптации, используются только в закрытой оценке. Одна задача с gold SQL из [HYDRA_PILOT.md](HYDRA_PILOT.md) проверяет инструменты и не заменяет самостоятельный benchmark-прогон агента.

## Закрытый бенчмарк текстового поиска

Сборка создаёт SQLite FTS5/BM25 и, при `--faiss`, FAISS с нормализованными векторами документов Jina v5 Text Small Retrieval GGUF Q4_K_M. `llama.cpp` вычисляет эмбеддинги через `POST /v1/embeddings`. `dense` ищет по косинусному сходству в FAISS, `bm25` использует SQLite FTS5, `hybrid` объединяет оба ранжирования через RRF с параметром 60. Все workers разделяют готовые снимки. Запросы кодируются в режимах `dense` и `hybrid`. [Архитектура поиска](RAG_SEARCH.md#локальные-bm25-и-jinafaiss).

На Apple Silicon нужны `llama-server` и сборка с Metal. Скрипт обнаруживает [llama.cpp b12500](https://github.com/ggml-org/llama.cpp/releases/tag/b12500) по пути `data/llama.cpp/b12500/llama-b12500/llama-server` или в `PATH`; путь можно задать через `LLAMA_SERVER`. Скачайте [закреплённый GGUF Jina](https://huggingface.co/jinaai/jina-embeddings-v5-text-small-retrieval-GGUF/blob/78b0ebcb4c870fdfef409e578b65288b49a4fa90/v5-small-retrieval-Q4_K_M.gguf) в `models/jina-embeddings-v5-text-small/v5-small-retrieval-Q4_K_M.gguf`. Скрипт проверяет SHA-256 файла. API слушает только loopback. Для клиента значение `--embeddings-url` включает `/v1`.

```bash
python -m pip install -e '.[dev,environments]'
scripts/serve-jina-embeddings.sh
```

В другом терминале проверьте готовность и alias модели.

```bash
curl -fsS http://127.0.0.1:8081/health
curl -fsS http://127.0.0.1:8081/v1/models
```

После запуска сервера соберите снимок. В JSONL каждая строка содержит `doc_id`, `text` и, при наличии, `title` и `language`. Одна строка соответствует одной единице поиска. Для корпуса с чанками используйте уже нарезанные фрагменты и исходные идентификаторы. Длинные записи нужно подготовить в пределах контекста эмбеддера до построения индекса.

```bash
.venv/bin/python examples/run_text_retrieval.py build \
  --corpus data/text-retrieval/corpus.jsonl --corpus-id my-text-corpus \
  --bm25 data/text-retrieval/bm25.sqlite --faiss data/text-retrieval/faiss
```

Команда `run` принимает TSV из двух колонок `query_id` и `query`. По умолчанию она фиксирует первые 100 ID в порядке файла и записывает ревизию, хеш вопросов, индекс, настройки модели, историю, события и расходы. `--direct` выполняет один поиск по исходному вопросу без API-вызова LLM. Для запуска агента через Eliza/OpenRouter используйте `--model-id qwen/qwen3.6-35b-a3b`, `--budget-usd`, `--request-reserve-usd` и `--openrouter-max-price INPUT OUTPUT`. Формат локального `.env` описан в [HYDRA_PILOT.md](HYDRA_PILOT.md#eliza-и-openrouter). После прерывания оценщик может прочитать уже сохранённые эпизоды и показать покрытие. Автоматическое продолжение `run` пока не реализовано.

Агент использует до пяти раундов. Размер рабочего контекста оценивается по длине JSON в UTF-8, делённой на четыре. При 75% от 32 768 оценочных токенов текущий раунд перестаёт предлагать поиск. Через `save_and_advance` модель переносит выбранные фрагменты, резюме, нерешённые вопросы и цель. Политика `bounded` ограничивает число ходов и сохраняет резервную выдачу. [Агентный режим](#агентный-поиск-с-отдельной-финализацией).

Отдельная оценка с TREC `qrel_evidence.txt` выполняется после записи траекторий. Для TRuST сначала берутся первые десять позиций, затем чанки сворачиваются к родительскому ID. В отчёте есть средний Recall@10, recall всех показанных свидетельств, доля оценённых задач, причины остановки, p50/p95 и стоимость. Инфраструктурные сбои снижают покрытие. Пустой итоговый список в оценённом эпизоде даёт нулевой Recall@10.

Пример требует доступного локального HTTP-процесса над публичным индексом TRuST и его манифеста `index.json`. Раннер подключается к готовому сервису через `--reference-url`. Манифест должен содержать `corpus_id`, `corpus_revision` и `search_revision`. [HTTP-контракт T-Search](https://github.com/turbo-llm/t-search-harness#search-backend-contract).

```bash
.venv/bin/python examples/run_text_retrieval.py run \
  --benchmark trust --dataset-revision 074a7ac05ddf2e79ac31f96e225c069057ff1095 \
  --questions data/text-retrieval/trust/queries.tsv \
  --reference-url http://127.0.0.1:8000 --reference-manifest data/text-retrieval/trust/index.json \
  --direct --count 100 --output runs/trust-direct

.venv/bin/python examples/run_text_retrieval.py evaluate \
  --run runs/trust-direct --qrels data/text-retrieval/trust/qrel_evidence.txt \
  --report runs/trust-direct-recall.json
```

### Прямой BM25 на BrowseComp-Plus EN

Подготовка выбирает первые 100 вопросов в исходном порядке, читая колонки `query_id` и `query` из публичного Parquet. Положительные qrels закреплены отдельной ревизией. Флаг `--with-bm25` скачивает готовый Lucene-индекс полного корпуса объёмом 2,17 ГБ и записывает хеши всех его файлов. [Опубликованный индекс](https://huggingface.co/datasets/Tevatron/browsecomp-plus-indexes/tree/b3f37f70c33829eb09d04784a54277a31871fd63/bm25).

```bash
uv pip install --python .venv/bin/python pyarrow huggingface-hub hf_xet JPype1
.venv/bin/python examples/prepare_browsecomp_plus.py --count 100 --with-bm25
```

Для сервера нужны Java 21 и [Anserini 1.2.1 fat JAR](https://repo.maven.apache.org/maven2/io/anserini/anserini/1.2.1/anserini-1.2.1-fatjar.jar). Сохраните JAR по пути из команды ниже. Если JPype не находит Java по `JAVA_HOME`, путь к библиотеке JVM можно передать через `--jvm`.

```bash
.venv/bin/python examples/serve_browsecomp_bm25.py \
  --index data/text-retrieval/browsecomp-plus/index/bm25 \
  --manifest data/text-retrieval/browsecomp-plus/bm25.json \
  --anserini-jar data/text-retrieval/browsecomp-plus/runtime/anserini-1.2.1-fatjar.jar
```

В другом терминале запустите прямой поиск и оценку.

```bash
.venv/bin/python examples/run_text_retrieval.py run \
  --benchmark browsecomp-plus --dataset-revision 144cff8e35b5eaef7e526346aa60774a9deb941f \
  --questions data/text-retrieval/browsecomp-plus/input/queries.tsv \
  --reference-url http://127.0.0.1:8091 \
  --reference-manifest data/text-retrieval/browsecomp-plus/bm25.json \
  --direct --count 100 --concurrency 4 --output runs/browsecomp-plus/bm25-direct100

.venv/bin/python examples/run_text_retrieval.py evaluate \
  --run runs/browsecomp-plus/bm25-direct100 \
  --qrels data/text-retrieval/browsecomp-plus/input/qrel_evidence.txt \
  --report runs/browsecomp-plus/bm25-direct100/evaluation.json
```

### Плотный контроль Qwen3-Embedding-8B

Скачиваем четыре опубликованных шарда BrowseComp-Plus общим объёмом 1,64 ГБ. Сборка проверяет их SHA-256 и складывает 100 195 готовых векторов размерности 4096 в FAISS `IndexFlatIP`. Тексты по найденным ID читаются из готового Lucene-корпуса. Оба бэкенда возвращают до 2000 символов сниппета. [Публичные шарды](https://huggingface.co/datasets/Tevatron/browsecomp-plus-indexes/tree/b3f37f70c33829eb09d04784a54277a31871fd63/qwen3-embedding-8b).

```bash
.venv/bin/hf download Tevatron/browsecomp-plus-indexes --repo-type dataset \
  --revision b3f37f70c33829eb09d04784a54277a31871fd63 \
  --include 'qwen3-embedding-8b/*' --local-dir data/text-retrieval/browsecomp-plus/index

.venv/bin/python examples/serve_browsecomp_dense.py --build-only \
  --bm25-manifest data/text-retrieval/browsecomp-plus/bm25.json \
  --shards data/text-retrieval/browsecomp-plus/index/qwen3-embedding-8b \
  --snapshot data/text-retrieval/browsecomp-plus/qwen-faiss
```

Для кодирования запросов сервер использует токен Eliza из локального `.env` и маршрут Eliza → OpenRouter `/raw/openrouter/v1/embeddings`. Префикс запроса взят из публичной реализации BrowseComp-Plus. Для запуска задайте согласованный бюджет в `EMBEDDING_BUDGET_USD`. Общий сервер принимает запросы от нескольких прогонов, по умолчанию до четырёх одновременно отправляет в Eliza, остальные ставит в очередь. Поле `--embedding-concurrency` задаёт верхний предел. После таймаута или обрыва соединения сервер делает один повтор. Резерв исходного запроса остаётся в `unsettled_reservation_usd`, остальные эпизоды продолжаются в рамках бюджета. Если API сообщает токены без стоимости, используется верхняя цена из конфигурации маршрутизации. [Префикс запроса](https://github.com/texttron/BrowseComp-Plus/blob/046949032b0328319cc9a02663a759ec601d9402/searcher/searchers/faiss_searcher.py).

```bash
.venv/bin/python examples/serve_browsecomp_dense.py \
  --bm25-index data/text-retrieval/browsecomp-plus/index/bm25 \
  --bm25-manifest data/text-retrieval/browsecomp-plus/bm25.json \
  --snapshot data/text-retrieval/browsecomp-plus/qwen-faiss \
  --anserini-jar data/text-retrieval/browsecomp-plus/runtime/anserini-1.2.1-fatjar.jar \
  --budget-usd "$EMBEDDING_BUDGET_USD" \
  --service-manifest data/text-retrieval/browsecomp-plus/qwen-service.json
```

В команде прямого поиска используйте `--reference-url http://127.0.0.1:8093` и `--reference-manifest data/text-retrieval/browsecomp-plus/qwen-service.json`. Вопросы, qrels, отсечение top‑10 и оценщик совпадают с прямым BM25. До остановки сервера сохраните ответ `GET /usage` в `embedding-usage.json` в каталоге прогона. `evaluate` сверяет ID сессии и добавляет этот файл в отчёт. Поле `summary.known_cost_usd` относится к вызовам модели агента, а `embedding_usage.reported_cost_usd` содержит стоимость векторов из API.

### Агентный пилот на том же индексе

Для агентного прогона вместо `--direct` задайте `--model-id qwen/qwen3.6-35b-a3b` и согласованный бюджет модели. Исходный пилот воспроизводится с `--retrieval-policy baseline`. Он использует тот же FAISS и первые десять ID из прямого прогона, до пяти раундов, лимит 16 384 выходных токена на ответ, seed 42 и сниппеты до 2000 символов. После таймаутов первого запуска закрепили транспортные параметры `--openrouter-provider parasail/fp8` и `--request-timeout 240`.

При явном HTTP 401 агентный раннер и сервер эмбеддингов делают один повтор после паузы. При таймауте запроса генерации его резерв остаётся учтённым, а оставшиеся задачи могут использовать свободный бюджет. Предел генерации и отсутствие `finish` считаются результатами модели. Таймауты и сбои доставки уменьшают покрытие. В первой серии агентного режима оценены 2 из 10 вопросов. При масштабировании до 90 задач серия получила HTTP 401 ещё до завершения первого эпизода и не дала оцениваемых ответов. Эти попытки хранятся отдельно от повторного пилота.

### Агентный поиск с отдельной финализацией

Режим `--retrieval-policy bounded` используется по умолчанию в агентном CLI. Он начинает с поиска по исходному вопросу, отключает reasoning через OpenRouter, выделяет до 2048 выходных токенов на ответ и ограничивает цикл 12 вызовами модели. Промпт направляет агента на короткие запросы по конкретным пробелам в доказательствах. По принципу `smolagents` последний ход выделен для финализации. Модель получает краткий список до 20 найденных документов и один инструмент `finish`. [Реализация финализации smolagents](https://github.com/huggingface/smolagents/blob/main/src/smolagents/agents.py) · [Параметры reasoning OpenRouter](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

По умолчанию Qwen3.6-35B-A3B в режиме `bounded` получает до 256 токенов текста на результат. Лимит применяется к исходному сниппету до записи наблюдения. Стартовый поиск, обычный поиск и финализация используют уже обрезанные фрагменты. Идентификаторы, позиции и порядок выдачи сохраняются. Манифест хранит лимит и SHA-256 токенизатора в `search_observation`. Для первого запуска скачайте закреплённый `tokenizer.json` без весов модели. Пакет `tokenizers` входит в `.[environments]`.

```bash
mkdir -p data/text-retrieval/tokenizers/qwen3.6-35b-a3b
curl -fsSL \
  https://huggingface.co/Qwen/Qwen3.6-35B-A3B/resolve/fc09a87769c63a4c45d08766dc9602ae2c8e2c10/tokenizer.json \
  -o data/text-retrieval/tokenizers/qwen3.6-35b-a3b/tokenizer.json
```

Для другого токенизатора укажите `--search-snippet-tokens 256 --search-tokenizer /path/to/tokenizer.json`. Для воспроизведения прежней выдачи BrowseComp-Plus укажите `--search-snippet-chars 2000`, для короткого символьного варианта — `--search-snippet-chars 700`. `--max-steps 24` меняет общий потолок вызовов модели на эпизод, включая ход финализации. `--max-tokens 8192` повышает потолок генерации на отдельном вызове, а `--reasoning-effort low` отправляет запрошенный уровень через OpenRouter и записывает его в манифест. Применение уровня на конкретном маршруте проверяем по `completion_tokens_details.reasoning_tokens` и результату вызова инструмента.

В опубликованном сравнении T-Search лимит сниппета составляет 512 токенов. Шаблон поисковой модели включает thinking по умолчанию, а харнесс хранит его между ходами текущего раунда. Отдельная модель в демо пишет пользовательский ответ с reasoning off. [Настройки T-Search](https://huggingface.co/t-tech/T-Search#reference-sglang-serving-setup) · [Протокол сравнения](https://arxiv.org/html/2610.06782#S6).

Резервная выдача объединяет результаты уникальных запросов по RRF. Ранжирование исходного вопроса получает двойной вес. При остановке по лимиту или невалидному ответу эта выдача возвращает уже собранные свидетельства. После успешного `finish` выбранные моделью ID остаются первыми, а резерв дополняет список до десяти. `ranking_source` различает источники итогового ранжирования. Сбой инфраструктуры остаётся отдельным исходом.

Для парного сравнения с прямым поиском используйте один порядок вопросов, один снимок FAISS и одни qrels. Первый прогон агентного режима берёт `--offset 0 --count 30`, второй — `--offset 30 --count 70`. Первые 10 ID использовались для разбора исходного сбоя. Следующие 90 оценивают уже зафиксированную конфигурацию. `Recall@10` измеряет полноту десяти итоговых документов, а `observed_evidence_recall` — полноту всех свидетельств, полученных в ходе поиска. Оценщик читает qrels после агентного прогона.

Команда первого прогона с запущенным сервером Qwen и согласованным бюджетом генерации в `MODEL_BUDGET_USD`. Для второго задайте `--offset 30 --count 70 --concurrency 10` и новый каталог результатов.

```bash
.venv/bin/python examples/run_text_retrieval.py run \
  --benchmark browsecomp-plus --dataset-revision 144cff8e35b5eaef7e526346aa60774a9deb941f \
  --questions data/text-retrieval/browsecomp-plus/input/queries.tsv \
  --reference-url http://127.0.0.1:8093 \
  --reference-manifest data/text-retrieval/browsecomp-plus/qwen-service.json \
  --model-id qwen/qwen3.6-35b-a3b --retrieval-policy bounded --search-snippet-chars 2000 \
  --openrouter-provider parasail/fp8 --openrouter-max-price 0.10 0.90 \
  --request-timeout 120 --budget-usd "$MODEL_BUDGET_USD" --request-reserve-usd 0.04 \
  --offset 0 --count 30 --concurrency 6 --output runs/browsecomp-plus/agent-first30
```

### План замеров на публичных наборах

1. **Первый воспроизводимый baseline.** Закрепить 100 ID BrowseComp-Plus EN, хеши вопросов, qrels и полный публичный корпус. Подключить опубликованный Lucene/BM25-индекс через адаптер `ReferenceSearch` и прогнать `--direct` без API-вызовов модели. Проверить, что выбранные ID имеют положительные qrels и что ID выдачи совпадают с единицей оценки. Зафиксировать Recall@10, покрытие, настенное время прогона и p50/p95. [Публичные данные и индексы BrowseComp-Plus](https://github.com/texttron/BrowseComp-Plus#downloading-pre-built-indexes).
2. **Локальная скорость и вклад BM25.** Проверить Metal в обычном терминале Mac и снять p50/p95, пропускную способность и пиковую память после одинакового прогрева. Сравнить локальные `bm25` на SQLite, `dense` и `hybrid` на одних вопросах, полном корпусе, глубине выдачи и одном снимке. Индекс Jina подготовить один раз на подходящей машине и переиспользовать. Для разницы Recall@10 посчитать парный интервал по задачам. Если прирост от BM25 мал относительно разброса и затрат, оставить `dense` кандидатом на локальный режим по умолчанию.
3. **Контрольный ретривер и агентный baseline.** Для прямого и агентного замера подключить опубликованный Qwen3-Embedding-8B-индекс BrowseComp-Plus и кодировать запросы тем же эмбеддером. Это плотный ретривер из статьи T-Search. Для агентных прогонов зафиксировать наш харнесс, генератор Qwen3.6-35B-A3B через Eliza, промпты, схемы инструментов, лимиты и объём сниппетов. Сначала короткий пилот для оценки времени и затрат, затем сравнение поиска с теми же бэкендами и 100 ID. Наш результат на подвыборке и опубликованные результаты T-Search по полному набору приводятся с указанием разных протоколов. [Протокол T-Search](https://arxiv.org/html/2610.06782#A3.SS4).
4. **Русскоязычная проверка.** Повторить измерение на первых 100 зафиксированных вопросах TRuST после подключения публичного корпуса и индекса. ru-BrowseComp-Plus подключать после получения точных артефактов опубликованной локализации. [Публичный релиз TRuST](https://huggingface.co/datasets/t-tech/TRuST).

Для всех этапов используем опубликованные benchmark-артефакты и один замороженный состав задач на сравнение. Политика разрешённых источников и Eliza зафиксирована в [AGENTS.md](../AGENTS.md#data-and-service-access). После фиксации агентного baseline разбираем формулировки запросов, повторные поиски, состав сниппетов, отбор свидетельств и перенос между раундами. Изменения поискового инструмента и промптов проверяем по одному фактору на разработочной выборке. Итоговые qrels остаются у оценщика.

## Собственный поток

Готовим задачи SQL → поиск, поиск → SQL и объединение независимых источников. Включаем повторяющуюся ситуацию с новыми сущностями, новую схему, смену документа и возврат к старому семейству. Точный повтор помечаем отдельно. Сравниваем стационарный поток и смену распределения на парных порядках. Планируем несколько порядков/seed и группируем неопределённость по потокам или мирам.

## Сравнения

| Вариант | Что переносится между сессиями |
|---|---|
| Static | Фиксированный исходный промпт |
| Memory-only | Извлекаемые записи, эпизоды и процедуры в духе Hermes |
| Prompt-evolution | Опубликованная версия промпта после внутреннего replay |
| Prompt + skills | Та же политика отбора с разрешёнными изменениями текстовых процедур |

Сначала сравниваем первые три варианта. Затем отдельно проверяем skills при том же расписании и запуск по повторяющимся сигналам при том же пространстве кандидатов. Считаем расходы анализа всех эпизодов, в том числе когда обновление пропущено.

## Результаты

Для каждого варианта показываем качество первой попытки по типам задач, накопленную парную разницу со static, регрессии, полную стоимость и задержку. Сохраняем версии модели, данных, промптов и skills, seed, расходы critic/replay, события принятия/отклонения и снимки памяти. Локальный manifest достаточен для пилота, целевой трекинг — MLflow.

Для проверки критика независимо прогоняем родителя и принятую версию на одинаковых следующих задачах в исследовательском режиме. Сопоставляем его предпочтение с изменением внешней метрики, включая вредные обновления. Эта диагностика скрыта от оптимизатора, её расходы показываем отдельно. Размеры, бюджет, пороги, оценщики и повторы фиксируем до итоговых прогонов.
