# Автономный поиск: первый этап

Модуль `search/` загружает корпус, строит SQLite FTS5 и предоставляет поиск и
чтение без модели, сервера и GPU. Рабочий ориентир: тысячи RU/EN-документов и
16 параллельных эпизодов. Стандартные примеры харнесса пока используют моки;
настоящий индекс подключается через существующий `SearchBackend`.

## Данные и публикация

Вход — iterable `Document(doc_id, text, title="", language="und")`; CLI читает
JSONL. Пример — `examples/fixtures/corpus.jsonl`. Вопросы, qrels, ответы и gold SQL
не передаются. Корпус загружается потоком, целиком в Python-память не собирается.
Поля должны быть строками без NUL; id, язык и текст непустые. Повторный `doc_id`
во входе считается ошибкой. По умолчанию документ и заголовок ограничены
1 000 000 символов каждый; превышение отклоняется, исходник не обрезается.

Каждый снимок — отдельный SQLite-файл. Временный файл создаётся рядом с целевым;
после построения проверяются целостность SQLite и соответствие FTS документам.
Готовый файл публикуется через hard link без перезаписи существующего пути.
Нужна локальная файловая система с hard links. Одновременные одинаковые сборки
безопасны, другой манифест по занятому пути вызывает `SnapshotConflict`.
Сбой до публикации не делает частичный индекс доступным. При аварийном завершении
процесса может остаться `.search-build-*`; удалять его следует после остановки сборок.

Повторная загрузка пересобирает временный индекс для сравнения, но не меняет
готовый файл: это идемпотентность, не быстрый кэш импорта. Новые данные публикуются
по новому пути. Работающий снимок нельзя редактировать или заменять. Поиск
проверяет его манифест на каждом обращении; защита от злонамеренной подмены файла
с неизменным манифестом не входит в этот локальный прототип.

## Идентификаторы и версии

`doc_id` уникален внутри `corpus_id`. Единицу документа определяет исходный набор:
если это абзац с собственным id, нельзя автоматически объединять его в статью.
Текст хранится как передан, включая пробелы и переносы строк.

| Поле | Определение |
|---|---|
| `content_hash` | SHA-256 канонических записей по `doc_id`; включает текст, заголовок и язык |
| `corpus_revision` | По умолчанию хеш содержимого; можно явно задать исходную ревизию |
| `chunk_id` | Хеш id документа, хеша текста, правил разбиения и границ |
| `index_revision` | Хеш манифеста, включая содержимое, корпус, разбиение, алгоритм и SQLite |
| `search_revision` | Хеш версии обработки запроса и всех настроек `SearchConfig` |

Перестановка входных записей не меняет версии и id. Изменение текста сохраняет
`doc_id`, меняет хеш корпуса и фрагменты этого документа. Изменение размера
фрагментов меняет индекс и `chunk_id`, но не хеш содержимого.
Уникальность ручных имён ревизий вне одного пути обеспечивает владелец данных;
глобального реестра алиасов нет. Сохраняйте также `content_hash` и `index_revision`.

Снимок требует ту же версию SQLite, что при сборке; иначе его нужно пересобрать.
Побайтовая идентичность файлов после пересборки не обещается. Эксперимент отдельно
фиксирует commit и окружение. Манифест доступен через `backend.manifest`, результат
поиска включает использованные ревизии.

## Поиск и чтение

FTS5 индексирует заголовок и текст с одинаковым весом: `unicode61`, BM25 по
документам, при равных оценках сортировка по `doc_id`. Меньший BM25 score лучше.
Одна выдача содержит уникальные документы. Текст хранится в таблице документов,
индекс использует external content. Сниппеты вычисляются после отбора top-k.

Запрос нормализуется NFC; слова выделяются выражением `[^\W_]+`, объединяются
через OR и передаются как литералы в параметризованный MATCH. Пунктуация и слова
операторов не включают поисковый DSL. Пустой запрос, отсутствие слов и превышение
пределов — ошибка. Нет лемматизации, перевода, исправления опечаток и embeddings.
RU/EN означает поиск слов обоих языков, а не межъязыковой retrieval.

Сниппет берётся из тела документа около совпадений, до 48 токенов, затем ограничивается символами;
возможен разделитель ` … `, HTML не добавляется. Это выдержка, а не весь документ.
Если совпал только заголовок, возвращается начало тела; чтение возвращает тот же исходный текст.
Фрагменты `chars-v1` — последовательные непересекающиеся отрезки по 2000 символов
по умолчанию. Конкатенация восстанавливает исходный текст. Границы абзацев и
overlap отложены до проверки на данных. Смещения — Unicode code points, как в Python str.

`read_document` / `read_chunk` возвращают `text`, `offset`, `next_offset`,
`total_chars`, `doc_id`, необязательный `chunk_id` и ревизию. У чанка offset
относителен началу чанка. `next_offset=null` означает конец. Смещение ровно в
конец даёт пустой текст, за конец — ошибку. `list_chunks` возвращает страницу id
в порядке исходного текста. Ранжирование по фрагментам в первую версию не входит.

| SearchConfig | По умолчанию |
|---|---:|
| `max_results` | 100 |
| `snippet_chars` | 500 |
| `max_read_chars` | 8000 |
| `max_query_chars` / `max_query_terms` | 2000 / 32 уникальных термина |
| `workers` / `max_pending` | 4 / 32 выполняемых и ожидающих операции суммарно |
| `timeout_seconds` | 5 секунд, включая очередь |

Число результатов не ограничивает число поисков в эпизоде. Харнесс дополнительно
ограничивает наблюдение. Все настройки влияют на `search_revision`.

## Параллельность, ошибки и журнал

Один `LocalSearch` принадлежит одному event loop и закрывается через `async with`.
SQLite выполняется в ограниченном ThreadPoolExecutor. Операция открывает собственное
read-only соединение в выполняющем её потоке и закрывает его там же. Общее соединение
между потоками не используется; очередь ограничена до отправки работы executor.
Нет состояния диалога или списка показанных агенту id.

Deadline включает очередь и выполнение. Progress handler SQLite проверяет остановку
каждые 1000 VM-инструкций. Отмена посылает сигнал; место занято до фактического
завершения worker. `aclose` останавливает остаток работ и ждёт освобождения ресурсов.
Это не жёсткая изоляция зависшего файлового I/O; сетевые файловые системы не поддерживаются.

| Ситуация | Результат |
|---|---|
| Нет совпадений | Успех, пустой `hits` |
| Неверный запрос / пределы | `InvalidRequest` |
| Неизвестный id / корпус / ревизия адаптера | `UnknownId` |
| Путь занят другим снимком | `SnapshotConflict` |
| Очередь заполнена | `SearchBusy` |
| Deadline / остановка SQLite | `SearchTimeout` |
| Отсутствующий, повреждённый или несовместимый снимок | `StorageError` |
| Отмена вызывающей задачи | `asyncio.CancelledError` |

Логгер `search_rl_env.search.backend` на INFO выдаёт JSON: операция, статус,
длительность, очередь, исполнение, число результатов и версии. При timeout/отмене
незавершённые замеры worker равны `null`. Запросы, тексты, id чтения и сырые
исключения в лог не включаются. Назначение логов настраивает вызывающее приложение.

## Подключение и следующие этапы

```python
from search_rl_env.search import HarnessSearch, LocalSearch

async with LocalSearch("indexes/demo.sqlite") as backend:
    search = HarnessSearch(backend)
    # await run_episode(task, model, search, config)
```

Адаптер возвращает существующий `list[SearchHit]`: `doc_id`, `snippet`, `rank`.
`corpus_revision=None` выбирает уже открытый снимок, а не изменяемую «последнюю»
версию. Явная неверная ревизия отклоняется. Владелец runner сохраняет манифест и
`search_revision`; в EpisodeResult они автоматически не добавляются. Харнесс
трактует исключения поиска как infrastructure_error. Проверка показанных id
остаётся у харнесса; инструмента read у агента пока нет.

Unit-тесты покрывают версии, конкурентную загрузку, ранжирование, Unicode,
чтение, ошибки, лимиты, 16 параллельных обращений, отмену, реальный SQLite-timeout
и телеметрию без текстов. Интеграция проверяет 16 эпизодов MockModel с настоящим поиском.

`examples/benchmark_search.py` строит временный RU/EN-корпус и прогревает индекс.
Замер — closed-loop batch с частыми, редкими и отсутствующими словами. p50/p95
включают очередь, относятся к успешным запросам; ошибки учитываются отдельно,
exit code при них ненулевой. Вывод включает параметры, окружение, версии, размер
и время сборки. Искусственные повторяющиеся тексты не оценивают реальное качество.

Локальные измерения 2026-11-07: Python 3.12.13, SQLite 3.53.1, macOS ARM64;
160 запросов, concurrency=16, workers=4, прогретый индекс:

| Документов | Базовая длина, символы | Сборка | Индекс | p50 / p95 | Успешных запросов/с |
|---:|---:|---:|---:|---:|---:|
| 10 000 | 2 000 | 1,60 с | 48,1 МБ | 255 / 282 мс | 71,1 |
| 10 000 | 32 000 | 23,00 с | 546,3 МБ | 462 / 523 мс | 37,8 |

Оба запуска завершили 160/160 запросов без ошибок. В отдельном коротком сценарии
workers=1 дал p95 156 мс и 110,8 успешных запросов/с: больше потоков не гарантирует
ускорение. Параметр остаётся настраиваемым; выбирать его для настоящего корпуса
нужно по отдельным измерениям. Эти результаты не являются согласованным SLO.

С Вовой нужны небольшой реальный корпус, лицензия, id, единица оценки и длины;
с Сергеем — необходимость read и формат ошибок; с Колей — запись манифестов и
нагрузочный протокол. Для другого движка сохраняются исходные данные/id и
SearchBackend, индекс пересобирается с новой версией. SQL и HTTP в этот этап не входят.
