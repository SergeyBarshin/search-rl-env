# Поиск: Go-сервис и Python-адаптер

Первая версия участка Димы: отдельный Go-сервис загружает корпус, хранит снимки,
индексирует документы и предоставляет HTTP API. Python-клиент реализует существующий
`SearchBackend` Сергея. Рабочий масштаб — тысячи RU/EN-документов и 16 параллельных
эпизодов. Для одной HyDRA-задачи добавлен опциональный read-only SQL API; инструменты агента и оценщики сохраняют прежние контракты. Стандартный UI пока использует моки.

```text
JSONL → Go build → SQLite FTS5-снимок
                         ↑
Харнесс Python → SearchClient → HTTP → Go serve
```

## Запуск

Нужен Go 1.25+. Драйвер `modernc.org/sqlite v1.44.3` зафиксирован в go.mod/go.sum;
SQLite включена в бинарник. Сборка без CGO и системной SQLite проверяется через
`CGO_ENABLED=0 go build`. При первом запуске Go скачивает зависимости, модели не нужны.
Из корня репозитория:

```bash
go -C services/search build -o ../../build/search-service ./cmd/search
./build/search-service build
./build/search-service serve -snapshot indexes/hydra.sqlite -listen 127.0.0.1:8090
```

В другом терминале, после установки Python-пакета:

```bash
.venv/bin/python examples/run_search.py search --query 'Toronto Arenas'
.venv/bin/python examples/run_search.py read --doc-id 14900050
.venv/bin/python examples/run_search.py chunks --doc-id 14900050
.venv/bin/python examples/run_search.py episode --query 'Toronto Arenas'
```

Ожидаются KILT passage ids, исходный текст и законченный retrieval-эпизод MockModel. Полный SQL/search replay одной реальной задачи — в [HYDRA_PILOT.md](HYDRA_PILOT.md).
Другой адрес: `examples/run_search.py --url http://127.0.0.1:8091 search --query ...`.
Ctrl+C/SIGTERM отменяет активные запросы, останавливает HTTP и закрывает пул SQLite.
Для другого корпуса задайте свой JSONL и новый путь снимка.

## Границы и версии

В Go находятся `services/search/internal/search/` и CLI `cmd/search`. Python
`src/search_rl_env/search/` содержит только HTTP-клиент, типы и ошибки протокола.
Он не запускает сервис и не содержит SQLite, индексации или ранжирования.
Транспорт — stdlib net/http; готовый индекс один на экземпляр сервиса.

Вход JSONL: `doc_id`, `text`, необязательные `title` и `language` (по умолчанию `und`).
Неизвестные поля отклоняются; вопросов, qrels, ответов и gold SQL здесь нет.
Загрузка потоковая, весь корпус в памяти не собирается. Текст и заголовок ограничены
1 000 000 Unicode code points каждый, строка JSONL — 16 МиБ. NUL, пустые id/тексты
и повторные doc_id отклоняются. Превышение размера не обрезает исходник.
Некорректный UTF-8 и непарные surrogate в JSON-escape отклоняются до декодирования,
чтобы не подменять исходные символы знаком замены.

`doc_id` сохраняется из набора и уникален внутри корпуса. Единицу поиска задаёт
источник и разметка Вовы: абзац с собственным id нельзя объединять в статью автоматически.
Фрагменты `chars-v1` — непересекающиеся отрезки по 2000 символов, размер задаёт
`build -chunk-chars`. Их конкатенация восстанавливает текст. Смещения в Go и Python
считаются в Unicode code points, не байтах. Семантическое разбиение пока не вводится.

| Поле | Содержание |
|---|---|
| `content_hash` | SHA-256 канонических записей `[id,text,title,language]` по doc_id |
| `corpus_revision` | Ревизия источника; по умолчанию content_hash |
| `chunk_id` | Хеш id, текста документа, правил разбиения и границ |
| `index_revision` | Хеш манифеста, содержимого, разбиения, алгоритма и драйвера/SQLite |
| `search_revision` | Версия обработки запроса, конфигурация сервиса и версия Go |

Порядок входа не меняет версии и id. Изменение текста сохраняет doc_id и меняет
ревизию содержимого и фрагменты документа. Изменение разбиения меняет индекс,
но не content_hash. Ручные названия ревизий вне одного пути контролирует владелец
данных; глобального реестра алиасов нет. Записывайте весь манифест, не только имя ревизии.
Go-JSON канонизация имеет собственные правила экранирования: совпадение всех хешей
с прежним Python-прототипом для произвольного Unicode не является контрактом.

Сборка создаёт временную SQLite рядом с целевым файлом, проверяет целостность БД
и соответствие FTS документам, затем публикует hard link без перезаписи пути.
Нужна локальная файловая система с hard links. Повторная идентичная сборка безопасна;
другой снимок по занятому пути даёт snapshot_conflict. Новые данные — новый файл.
Повторная сборка пересоздаёт временный индекс для сравнения; это не быстрый кэш.
При аварии процесса возможен оставшийся `.search-build-*`; удалять его можно после остановки сборок.

Снимки Python-прототипа schema_version=1 не поддерживаются: пересоберите из JSONL
Go-командой в новый файл. Текущая схема — 2; служба проверяет схему, алгоритм,
драйвер и встроенную версию SQLite. Редактирование/замена обслуживаемого файла
запрещены. Проверяются inode/размер/mtime и манифест соединения; это не защита от
злонамеренной подмены администратором локальной машины. Сетевые файловые системы не поддерживаются.

## HTTP API v1

Сервис по умолчанию слушает loopback. Аутентификация/TLS не реализованы; внешний
доступ требует отдельно согласованного размещения. Для локального harness они не нужны.
API описан как первая версия нашей интеграции; расширения общих инструментов
нужно согласовывать с Сергеем. Каждый успешный ответ данных включает corpus_id,
corpus_revision, index_revision и search_revision.

| Метод и путь | Вход | Ответ |
|---|---|---|
| GET /healthz | — | `{"status":"ok"}` при доступном снимке |
| GET /v1/manifest | — | Манифест, api_version="1", search_revision и config |
| POST /v1/search | corpus_id, corpus_revision?, query, limit? | hits: doc_id, snippet, rank, score |
| POST /v1/read | корпус/ревизия, ровно один doc_id или chunk_id, offset?, limit? | text, doc_id, chunk_id, offset, next_offset, total_chars |
| POST /v1/chunks | корпус/ревизия, doc_id, offset?, limit? | chunk_ids, next_offset |

`corpus_revision=null`/отсутствие выбирает снимок этого экземпляра, а не «последнюю»
версию. Python-клиент запрашивает манифест при открытии и далее передаёт явную ревизию.
Он проверяет версии каждого ответа, уникальность/rank результатов, размер текста
и границы чтения. Смена окружения во время прогона — SearchProtocolError.

Поиск: FTS5 unicode61, BM25 по документам, одинаковый вес заголовка и текста;
при равных score сортируем по doc_id. Меньший внутренний score лучше.
Слова запроса — Unicode letters/numbers, дубликаты по нижнему регистру удаляются;
термины экранируются как литералы и объединяются через OR в параметризованном MATCH.
Пунктуация не включает DSL. Нет лемматизации, перевода, embeddings и исправления
опечаток. RU/EN означает поиск слов обоих языков, не межъязыковой retrieval.

Сниппет из тела строится после top-k, до 48 токенов и ограничения символов, без HTML.
При совпадении только заголовка возвращается начало тела. Чтение возвращает тот же
исходный текст, а не нормализованный индекс. next_offset=null означает конец;
offset ровно в конец даёт пустой текст, за конец — ошибку. У чанка offset относителен
его началу. next_offset списка чанков — позиция следующей страницы.

| Ограничение | По умолчанию / флаг serve |
|---|---|
| Результатов | 100 / -max-results |
| Сниппет | 500 символов / -snippet-chars |
| Чтение | 8000 символов / -max-read-chars |
| Запрос | 2000 символов, 32 термина / -max-query-chars, -max-query-terms |
| Соединения SQLite | 4 / -workers |
| Выполняемые и ожидающие операции | 32 / -max-pending |
| Deadline с очередью | 5s / -timeout |
| HTTP body / headers | 64 КиБ / 16 КиБ |

Ожидание пула и SQL используют context; отмена клиента прерывает запрос драйвера.
Место остаётся занятым до возврата операции. database/sql переиспользует ограниченный
пул read-only соединений. Состояния эпизода и показанных id у сервиса нет.

Ошибки: `{"error":{"code":"...","message":"безопасное сообщение"}}`.
invalid_request → 400, unknown_id → 404, busy → 503, timeout → 504,
cancelled → 408, storage_error → 500. Пустая выдача — 200 с hits=[], не ошибка.
Сырые исключения/SQL/пути в ответ не включаются. Логи JSON на stderr содержат
статус, очередь/исполнение/общую длительность, число результатов и версии;
тексты запросов, документов и id чтения не записываются. Ошибки разбора HTTP
возвращаются до выполнения операции и не создают событие search_operation.

## Python и проверки

```python
from search_rl_env.search import SearchClient

async with SearchClient("http://127.0.0.1:8090") as search:
    # await run_episode(task, model, search, config)
    manifest = search.manifest  # Сохранить рядом с результатами эксперимента.
```

Клиент возвращает существующий list[SearchHit] без score. Повторы запросов не делает,
общий HTTP deadline 10s, максимум ответа 2 МиБ. Ресурсом владеет вызывающий код.
Харнесс по-прежнему считает исключения поиска infrastructure_error; он же проверяет
показанные id. Инструмент read агенту пока не добавляется. EpisodeResult автоматически
манифест не получает: запись его в результат согласуется с Колей.

```bash
go -C services/search test -race ./...
go -C services/search vet ./...
.venv/bin/python -m pytest -q
.venv/bin/python examples/benchmark_search.py --concurrency 16 \
  --output runs/search-benchmark/go-http.json
go -C services/search test -run '^$' -bench BenchmarkSearch -benchtime=160x -cpu=16 ./internal/search
```

Go-тесты проверяют снимки, ошибки, Unicode, ранжирование, чтение, 16 параллельных
обращений, очередь и фактическое прерывание SQL по context. Python unit-тесты
проверяют HTTP-протокол без сети, а integration запускает настоящий Go-бинарник
на случайном loopback-порту и 16 эпизодов MockModel. Для integration нужен Go;
если его нет, pytest явно пропускает эти проверки. Все тесты бесплатные, без моделей.

HTTP benchmark работает с уже запущенным сервисом, прогревает запросы и включает
очередь и транспорт в p50/p95 успешных запросов. Ошибки считаются отдельно, exit code
при них ненулевой. Можно передать несколько `--query`. Go benchmark строит искусственные
корпуса на 1/10 тысяч документов и измеряет движок без HTTP; его ns/op — усреднённая
пропускная способность, не p95 отдельного запроса. Эти измерения не оценивают качество.

Локальная проверка 2026-11-08: macOS ARM64 / Apple M4 Pro, Go 1.25.11,
SQLite 3.51.2; 10 000 искусственных RU/EN-документов по 2000 символов плюс marker.
Сборка заняла 1,82 с, снимок — 48,1 МБ. HTTP batch: 160 запросов, concurrency=16,
workers=4, запросы `equipment`, `поставка`, `notincorpus`, `marker5000` по кругу.
Завершено 160/160 без ошибок, p50=78,5 мс, p95=125,5 мс с транспортом и очередью,
186,2 успешных запроса/с. Это отдельный искусственный workload, не SLO и не
сопоставимое доказательство ускорения относительно прежнего Python-прототипа.

Дальше с Вовой нужны реальные RU/EN-данные, лицензии и единица оценки; с Сергеем —
необходимость read и ошибки инструментов; с Колей — сохранение манифестов и протокол
нагрузки. Выбор нового движка не меняет исходные doc_id и SearchBackend, но требует
нового индекса и ревизии поиска.
