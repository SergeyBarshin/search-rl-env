# Дизайн открытой среды обучения поисковых агентов

> Здесь описывается отдельный эпизод SQL + RAG. Постоянная память — [MEMORY_CORE.md](MEMORY_CORE.md). В закрытой оценке она заморожена; в потоке использования обновляется после текущей оценки и разрешённого feedback. Оба режима — [EXPERIMENTS.md](EXPERIMENTS.md).

Целевая постановка — **Text-to-SQL + RAG**. Агент обращается к таблицам и документам через инструменты и сдаёт ответ. Текстовый бенчмарк использует тот же runtime и возвращает ранжированные свидетельства. [Постановка](AGENT_SCOPE.md) · [Контракты](CONTRACTS.md).

## Первый пример использования

Предлагаемый первый пример — поиск свидетельств по вопросу в фиксированном корпусе. Агент возвращает ранжированный список найденных документов. Качество проверяется по размеченным релевантным документам без LLM-судьи.

Начальная основная метрика — Recall@10: доля известных релевантных документов, попавших в первые десять уникальных результатов агента. Это предложение для первого примера; конкретный набор релевантности и единицу оценки фиксируем при выборе данных. Режим с финальным текстовым ответом может использовать другую проверяющую функцию при том же цикле среды.

## Задача и наблюдение

| Часть | Содержание |
|---|---|
| Доступно агенту | Вопрос, язык, инструменты и история наблюдений |
| Доступно среде | Id и ревизия корпуса, конфигурация поиска и ограничения эпизода |
| Доступно только оценщику | Эталонные документы или ответы, правила проверки и группа разбиения |

Qrels — размеченные соответствия между вопросами и релевантными документами. Эталонная разметка не передаётся агенту. Документ имеет постоянный `doc_id`, чанк — отдельный `chunk_id` и родительский `doc_id`. Адаптер набора задаёт единицу оценки: при оценке по документам несколько чанков одного документа дают одно попадание.

## Действия

| Действие | Аргументы | Результат |
|---|---|---|
| `search` | Текст запроса и необязательный `top_k` в раундовом режиме | Упорядоченные кандидаты с ID, сниппетами и рангом |
| `save_and_advance` | Выбранные ID, резюме, нерешённые вопросы и цель | Новый раунд текстового поиска с выбранным контекстом |
| `sql` | SQL-запрос при подключённой SQL-среде | Колонки и строки результата |
| `finish` | Упорядоченные id найденных свидетельств | Завершение эпизода и оценка результата |

Модель выбирает число поисков и момент завершения в пределах конфигурации. В раундовом режиме рабочий контекст пересобирается при переходе, а полная история остаётся в траектории. HTTP-бэкенд поддерживает чтение оригинального текста через свой API. Агент получает сниппеты через `search`. [Раундовый режим](RAG_SEARCH.md#контекст-между-раундами).

В `finish` разрешены только ранее показанные id. Повторы удаляются с сохранением порядка. Невалидный формат и придуманные id возвращаются модели ошибкой инструмента; число исправлений не ограничено отдельным счётчиком. Различаем добровольное завершение, исчерпание бюджета, невалидные действия и инфраструктурный сбой. При исчерпании бюджета харнесс сохраняет пустой финальный список и `truncated=true`, без дополнительного вызова модели. Показанные документы остаются в истории, поэтому recall поиска можно посчитать отдельно от отбора. Сбои сервиса учитываются отдельно от качества модели.

## Награда

Для первого примера предлагаем терминальную награду:

```text
R = |top_10_unique_document_ids ∩ relevant_document_ids|
    / |relevant_document_ids|
```

Формула описывает встроенную метрику локальных задач. В текстовом бенчмарке оценщик берёт первые десять позиций финального списка и применяет правила ID конкретного набора. Для TRuST это перевод чанков в родительские документы с последующим удалением повторов. Эталон должен содержать хотя бы один релевантный документ.

Основная цель — повысить качество поиска при фиксированных ограничениях эпизода. Штраф за стоимость не требуется в первой версии. Реальные затраты измеряются отдельно. Recall всех показанных документов и recall финального списка различаются: они показывают качество поиска и качество отбора результата. Отсутствие документа в неполных qrels не доказывает его нерелевантность.

Для задач с ответом подключается отдельный проверяющий код. В BrowseComp-Plus официальная accuracy свободного ответа использует LLM-судью; она публикуется отдельно от детерминированных retrieval-метрик. [Описание оценщика](https://github.com/texttron/BrowseComp-Plus/blob/main/docs/llm_as_judge.md).

## Интерфейс и обучение

Текущая реализация использует OpenAI Agents SDK. Python-интерфейс `run_episode(task, model, search, config)` используется раннером и UI.

Модель выбирает порядок и число вызовов `search`, `sql` и `finish`. Ошибки инструментов возвращаются в историю. Харнесс проверяет бюджет между ходами.

Первый этап фиксирует baseline статического агента. GEPA-подобный оптимизатор промптов и оценка памяти запланированы поверх публичного журнала. SFT и RL относятся к дальнейшему развитию. Внешние оценочные задачи и их эталоны исключены из оптимизации. [Матрица экспериментов](EXPERIMENTS.md).

Текст результатов инструментов сохраняется в истории и действиях публичного EpisodeResult. Формат обучения описывается отдельно.

## Журнал и воспроизводимость

Сохраняются версия схемы, id задачи и эпизода, split, seed, хеши корпуса, индекса, кода и конфигурации; ревизия модели, dtype, промпт и параметры декодирования; наблюдения, действия, результаты инструментов и обрезка контекста; причина завершения, финальный список и компоненты награды.

Публичный результат содержит вызовы поиска, входные и выходные токены, время модели и инструментов и API-расход при наличии usage. Недоступная стоимость сохраняется как `null`. Текстовый бенчмарк пишет локальные манифест, события и JSON эпизодов. Интеграция MLflow и возобновление обучения запланированы.

Воспроизведение сохранённого эпизода проверяет среду и оценщик. Новая модель может выбирать другие действия, поэтому её качество измеряется новыми роллаутами на тех же задачах и при тех же ограничениях.

## Связанный синтетический пример SQL + RAG

В сценарии `sql_rag` агенту доступны публичная схема таблицы, `search(query)` по регламенту и `sql(query)` по фиксированным заказам. SQL-мок исполняет SQLite-запросы в памяти с доступом только на чтение; выдача, ошибки и число SQL-вызовов входят в траекторию. Оба инструмента используют синтетические данные. Порядок действий выбирает агент.

Завершение: `finish(answer: list[str], document_ids: list[str])`, где answer — подходящие id заказов, document_ids — показанные документы-источники. Пустые списки допустимы. Награда размеченного примера — точное совпадение множества id ответа с приватным `reference_answer`. Ошибочные ответы получают 0, правильные 1, без эталона награда отсутствует. Эталоны не включаются в схему, вопрос или наблюдения.

Команда CLI — `python examples/run_episode.py --scenario sql_rag --model mock --verbose`. В UI выберите «SQL + RAG · компенсации заказов». Публичный результат версии 4 сохраняет `answer`, `sql_calls` и историю. Пример проверяет контракт и исполнение инструментов на синтетике.
