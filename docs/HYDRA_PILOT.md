# HyDRA: диагностический replay SQL и поиска

> Этот replay проверяет источники и инструменты. Пилот самообучающегося харнесса должен включать самостоятельный ответ, независимую оценку и последующее использование памяти: [PAPER_PLAN.md](PAPER_PLAN.md), [EXPERIMENTS.md](EXPERIMENTS.md).

Сохранены исходные fixtures train_a2s_4, BIRD hockey и 999 KILT-фрагментов.
Источники, ревизии и хеши находятся в examples/fixtures/hydra/provenance.json;
атрибуция — в [ATTRIBUTION.md](../examples/fixtures/hydra/ATTRIBUTION.md).

```bash
python examples/prepare_hydra.py
python -m search_rl_env.search.server build
python -m search_rl_env.search.server serve --sql-catalog configs/backend/sql-catalog.example.json
```

В другом терминале: `python examples/run_hydra.py`.
Скрипт передаёт эталонный SQL, проверяет результат и выполняет поиск по вопросу
и SQL-значениям. Это проверка инструментов без агента; специально выбранный
подкорпус не даёт официального HyDRA score. Ручной hit@10 не является оценкой
правильности финального ответа. Gold хранится отдельно от корпуса.

Опциональный --with-vectors требует `.[hydra]` и отдельно подготовленных весов;
он остаётся диагностическим FAISS/RRF-экспериментом. Новая Python HTTP-реализация
требует своего подтверждённого replay; прежние измерения не переносятся на неё.

## Десять реальных вопросов и HTML по каждой траектории

Для локальных индексов установите зависимости `.[dev,environments]`. Скрипт подготовки загружает публичные данные и завершает работу до вызовов модели.

```bash
.venv/bin/python examples/run_hydra_pilot10.py --prepare-only
```

Для запуска через Eliza используйте локальный `.env` и явно согласованный бюджет.
Конфиг
`configs/environments/hydra-pilot10.json` версии 8 задаёт десять разных
train-вопросов HyDRA по БД hockey и параллельность 10. На один эпизод отводится
до 20 ходов и 300 секунд. На последнем ходу агенту предлагается сдать ответ
через `finish`. Один ответ модели ограничен 16 384 токенами. Поиск возвращает
название и текст до десяти фрагментов. Харнесс передаёт полную историю этих
наблюдений и сохраняет `model_context_limit` при переполнении окна провайдера.
После ответа без инструмента харнесс до двух раз напоминает о `finish`.
Модель сама отправляет через `finish` ответ или сообщает о нехватке источников.
Веса модели и постоянная память не меняются.

Протокол OpenAI Agents SDK и сценарии восстановления проверяются локальным pytest. Затем `examples/run_hydra_pilot10.py` запускается с бюджетными флагами из следующего раздела.

### Eliza и OpenRouter

Для Eliza укажите в локальном `.env` URL Chat Completions с префиксом
`/raw`, `MODEL_AUTH_SCHEME=OAuth` и путь к файлу личного токена в
`MODEL_API_KEY_FILE`. Префикс сохраняет исходный формат Chat Completions.
Слаг модели можно передать через `--model-id`.

Для запуска с согласованным бюджетом укажите `--billing usd --budget-usd` и
`--request-reserve-usd`. Резерв включает стоимость поколения и входа по
верхней оценке. Агент и оценщик используют общий остаток бюджета.
`--openrouter-max-price INPUT OUTPUT` передаёт ограничения тарифов в
долларах за миллион токенов. Манифест фиксирует резерв и расходы из usage.

Первый запуск скачивает исходные train-вопросы HyDRA и BIRD hockey (6,9 МБ)
из закреплённых ревизий. Поиск `kilt_hybrid` работает по локальному снимку из
999 фрагментов KILT, собранному вокруг Toronto Arenas. Покрытие остальных
вопросов этим срезом ограничено. [Происхождение корпуса](../examples/fixtures/hydra/ATTRIBUTION.md).

У каждого эпизода собственная копия SQLite с индексом FTS5/BM25 и клон
FAISS `IndexFlatIP`. Один запрос ищет в обеих копиях индекса, после чего
reciprocal rank fusion с параметром 60 объединяет списки по id документа.
FAISS использует 1024-мерные нормированные векторы из хешированных слов.
В манифесте сохранены алгоритмы, SHA-256 обоих индексов и версия энкодера.
Выбор задач фиксирован порядком первых десяти разных вопросов по БД hockey.

Для текстовых бенчмарков используется отдельный Jina/FAISS-снимок на весь прогон и опциональный канал BM25. [Архитектура поиска](RAG_SEARCH.md#локальные-bm25-и-jinafaiss).

Агент получает final_question и публичную схему SQLite. Gold SQL, final_answer,
key_term и разложение задачи в промпт и индекс не передаются. Агент сам выбирает
SQL и поисковые запросы и формулирует свободный ответ. Контракт finish сохраняет
answer:list[str]: в этом пилоте это список из одной строки с полным ответом.
Текст, переданный одной строкой, сохраняется как список из этой строки.
После сохранения первых ответов отдельные вызовы настроенной внутренней
модели сравнивают вопрос, ответ и эталон по рубрике `hydra-answer-v1`.
Перефразы допустимы. Оценка 1 требует всех существенных фактов без
противоречий. Пустой ответ получает 0, а инфраструктурные ошибки и невалидные
вердикты уменьшают покрытие. При полном покрытии точность равна числу
правильных ответов, делённому на 10. При пропусках сохраняется диапазон
возможных значений. Это метрика диагностического train-пилота.

Новый каталог `runs/hydra-pilot10/<UTC>-<id>/` содержит manifest.json,
events.jsonl и `html/index.html`. Для каждой попытки сохраняются отдельные
HTML, EpisodeResult JSON и описание среды с ревизиями, схемой и ограничениями.
HTML показывает ходы модели, реальные аргументы и результаты SQL/search,
выбранные источники, финальный ответ, usage и cost, переданный API. Фактическое
списание проверяется по биллингу. В исторических артефактах `internal`
обозначает режим запуска, а неизвестный cost остаётся `null`.
Оценщик пишет `evaluation/judge.json`, отдельный вердикт для каждого
сохранённого эпизода и `evaluation/summary.json` с метрикой и расходами
оценщика. Публичные траектории сохраняются отдельно. HTML и сводку можно
пересобрать из файлов через `--rebuild-report` без вызовов модели.

```bash
.venv/bin/python examples/run_hydra_pilot10.py --rebuild-report runs/hydra-pilot10/RUN_ID
```

Для агентного прогона используйте разрешённый API Eliza. Для подготовки
публичных SQLite и вопросов вне кэша нужен доступ к Hugging Face.

одни и те же десять вопросов и десять параллельных сред.

Версия 6 показывает полный локальный фрагмент и оставляет модели `finish`
на последнем ходу. В версии 7 лимит одного ответа вырос с 4096 до 8192

списком. В версии 7 только один из двух правильных ответов указал документ.

Покрытие оценки в обоих прогонах составило 100%. В версии 7 три исходных
вердикта исчерпали бюджет токенов. Повторный оценщик использовал сохранённые
ответы, прежнюю рубрику и лимит в 4096 токенов. Исходная сводка и попытки
сохранены в `evaluation/summary-initial.json` и `evaluation/retries/`.
Известный расход по двум прогонам с оценкой составил 0,27153 USD.
Стоимость четырёх оборвавшихся запросов к оценщику неизвестна.

`qwen/qwen3.5-9b` и конфиг версии 5. Точность первых попыток составила

## Диагностический запуск с живой Википедией

Прогон `20261117T224902Z-c3b0a662` использовал OpenAI Agents SDK 0.24.0,
`qwen/qwen3.5-9b` и конфиг пилота версии 4. Из десяти первых попыток
оценщик вынес восемь вердиктов и подтвердил два правильных ответа. В обоих
эпизодах агент использовал SQL и поиск. Покрытие оценки составило 80%,
диапазон точности на всех десяти вопросах составил 20–40%. Один запрос агента
завершился по таймауту, один ответ оценщика имел невалидный формат.

Все десять сред работали параллельно и были закрыты после прогона.
Девять эпизодов завершились через `finish`, пять из них использовали оба
источника. Агент сделал 104 вызова модели, 47 вызовов SQL и 47 вызовов поиска.
Эпизоды заняли 227,2 секунды, полный прогон с оценкой — 259,4 секунды.
API сообщил 0,11906 USD известного cost агента и 0,00054 USD cost оценщика.
Расход прерванного запроса неизвестен. Запуск использовал режим `internal`.

В локальных артефактах сохранены девять ответов, десять траекторий и
46 уникальных поисковых выдач. Пересборка из файлов воспроизвела
`evaluation/summary.json` с тем же SHA-256.

## Предыдущие прогоны

Прогон `20261117T191546Z-4e9b07b5` выполнен командой пользователя с версией 1
конфига: 10 первых запросов модели достигли барьера, peak concurrency 10,
68 вызовов модели, 40 SQL и 43 search, 101,17 секунды. Все 10 сред закрыты.
Получено 0 финальных ответов: 8 max_steps и 2 missing_finish (пустые ответы
модели без инструмента). Статус completed описывал завершение runner, а не
успех задач. API сообщил суммарный cost 0,070917015 USD; billing=internal,
подтверждения денежного списания в артефактах нет.

Версия 2 устраняет жёсткий обрыв на восьмом ходу и добавляет восстановление
missing_finish. Эти изменения не устраняют нехватку источников: доступный
подкорпус в версии 2 покрывал не все вопросы. Версия 3 переключает источник
на всю текущую английскую Википедию и снимает дополнительные бюджеты.
Честный частичный ответ с указанием
отсутствующих доказательств считается завершением протокола, не правильным
решением benchmark-задачи.

Прогон SDK `20261117T224729Z-eec81c64` остановили после выявления ошибки
`invalidparammix` в MediaWiki. Для нескольких страниц API возвращает по одной
ревизии автоматически. После удаления параметра `rvlimit` контрольный запрос
вернул десять страниц. В версии 4 также ограничили количество ходов и размер
поисковых наблюдений, чтобы повторные запросы не затягивали пилот.
