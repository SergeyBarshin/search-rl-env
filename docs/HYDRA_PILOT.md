# HyDRA: диагностический replay SQL и поиска

> Этот replay проверяет источники и инструменты. Пилот самообучающегося харнесса должен включать самостоятельный ответ, независимую оценку и последующее использование памяти: [PAPER_PLAN.md](PAPER_PLAN.md), [EXPERIMENTS.md](EXPERIMENTS.md).

Сохранены исходные fixtures train_a2s_4, BIRD hockey и 999 KILT-фрагментов.
Источники, ревизии и хеши находятся в examples/fixtures/hydra/provenance.json;
атрибуция — в [ATTRIBUTION.md](../examples/fixtures/hydra/ATTRIBUTION.md).

```bash
python examples/prepare_hydra.py
python -m search_rl_env.search.server build
python -m search_rl_env.search.server serve --sql-catalog configs/backend/sql-catalog.example.json
```

В другом терминале: `python examples/run_hydra.py`.
Скрипт передаёт эталонный SQL, проверяет результат и выполняет поиск по вопросу
и SQL-значениям. Это проверка инструментов без агента; специально выбранный
подкорпус не даёт официального HyDRA score. Ручной hit@10 не является оценкой
правильности финального ответа. Gold хранится отдельно от корпуса.

Опциональный --with-vectors требует `.[hydra]` и отдельно подготовленных весов;
он остаётся диагностическим FAISS/RRF-экспериментом. Новая Python HTTP-реализация
требует своего подтверждённого replay; прежние измерения не переносятся на неё.

## Десять реальных вопросов и HTML по каждой траектории

```bash
sh scripts/run-hydra-pilot10.sh
```

Режим internal разрешён Сергеем для внутреннего API без денежного биллинга.
Модель, адрес, OAuth-схема и файл ключа берутся из существующего .env;
передавать ключ в аргументах не требуется. Фиксирован конфиг
`configs/environments/hydra-pilot10.json`: 10 разных train-вопросов HyDRA
по БД hockey, параллельность 10. В версии 3 не заданы ограничения числа ходов,
суммарных выходных токенов, генерации на ход, числа вызовов модели и времени
эпизода. История передаётся полностью, результаты поиска не обрезаются харнессом.
Ограничения самого API и физическое окно модели сохраняются. Переполнение
контекста классифицируется как model_context_limit с сохранением полной истории;
скрытая обрезка или автоматическое суммирование не применяются.
После ответа без вызова инструмента harness до двух раз напоминает о finish;
все исходные ответы, напоминания и usage сохраняются. Это восстановление
протокола, а не автоматическое сочинение ответа за модель. Текстовый отказ
или признание нехватки источников тоже подаётся через finish.
Веса модели и постоянная память не меняются.

Скрипт сначала проверяет native Trace и сценарии восстановления; при ошибках
реальная модель не вызывается. Для отдельного запуска после проверок:
`.venv/bin/python examples/run_hydra_pilot10.py --billing internal`.

Первый запуск скачивает исходные train-вопросы HyDRA и BIRD hockey (6,9 МБ)
из закреплённых ревизий. По умолчанию поиск выполняется по текущей английской
Википедии через MediaWiki API. Запросы выбирает агент. Каждая выдача содержит
полный wikitext найденных страниц, их page id, revision id, timestamp и постоянную
ссылку. Исходные ответы API и SHA-256 сохраняются в source-responses/; одинаковый
запрос в рамках прогона использует сохранённую выдачу. Глобальная ревизия живого
корпуса не фиксируется: replay опирается на сохранённые наблюдения.
Это расширенный диагностический пилот на реальных данных, не официальный
HyDRA score на KILT 2019. Источники и условия повторного использования:
[MediaWiki Search](https://www.mediawiki.org/wiki/API:Search),
[Revisions](https://www.mediawiki.org/wiki/API:Revisions),
[Wikipedia terms](https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use).
Режим search_backend=kilt_fixture остаётся доступен в конфиге для replay
прежнего среза из 999 фрагментов; при ошибке Википедии скрытого fallback нет.
Выбор — первые 10 разных вопросов БД hockey по порядку источника, без отбора
по качеству ответа и без замены отсутствующих вопросов синтетикой.

Агент получает final_question и публичную схему SQLite. Gold SQL, final_answer,
key_term и разложение задачи в промпт и индекс не передаются. Агент сам выбирает
SQL и поисковые запросы и формулирует свободный ответ. Контракт finish сохраняет
answer:list[str]: в этом пилоте это список из одной строки с полным ответом.
Автоматическая содержательная оценка ответа не добавляется; она требует
согласованного оценщика. Формат завершения и факт использования двух инструментов
фиксируются отдельно от правильности ответа.

Новый каталог `runs/hydra-pilot10/<UTC>-<id>/` содержит manifest.json,
events.jsonl и `html/index.html`. Для каждой попытки сохраняются отдельные
HTML, EpisodeResult JSON и описание среды с ревизиями, схемой и ограничениями.
HTML показывает ходы модели, реальные аргументы и результаты SQL/search,
выбранные источники, финальный ответ, usage и cost, переданный API. Это поле
не подтверждает фактическое списание денег; режим internal разрешён пользователем
как внутренний API без денежного биллинга. Неизвестный cost остаётся null.
Эталон доступен только в отдельном свёрнутом блоке
человеческого отчёта и не является наблюдением агента.

Отчёты автономны и открываются локально без сервера и внешних ресурсов.
Доступ к Hugging Face и внутреннему API нужен во время запуска. Из ограниченной
песочницы текущей сессии эти сети недоступны; наличие runner не означает,
что запросы к реальной модели уже выполнены из этой сессии.

## Первый реальный прогон и доработка

Прогон `20261117T191546Z-4e9b07b5` выполнен командой пользователя с версией 1
конфига: 10 первых запросов модели достигли барьера, peak concurrency 10,
68 вызовов модели, 40 SQL и 43 search, 101,17 секунды. Все 10 сред закрыты.
Получено 0 финальных ответов: 8 max_steps и 2 missing_finish (пустые ответы
модели без инструмента). Статус completed описывал завершение runner, а не
успех задач. API сообщил суммарный cost 0,070917015 USD; billing=internal,
подтверждения денежного списания в артефактах нет.

Версия 2 устраняет жёсткий обрыв на восьмом ходу и добавляет восстановление
missing_finish. Эти изменения не устраняют нехватку источников: доступный
подкорпус в версии 2 покрывал не все вопросы. Версия 3 переключает источник
на всю текущую английскую Википедию и снимает дополнительные бюджеты.
Честный частичный ответ с указанием
отсутствующих доказательств считается завершением протокола, не правильным
решением benchmark-задачи. Полную проверку native runner и повторный реальный
прогон после доработки ещё нужно выполнить: текущая песочница запрещает даже
bind на 127.0.0.1. Тесты восстановления с подставным транспортом доступны без TCP.
