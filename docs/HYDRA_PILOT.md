# HyDRA: одна задача, SQL и поиск по настоящему корпусу

Основной интеграционный пример теперь использует `train_a2s_4` из HyDRA-Bench,
а не искусственные заказы и регламент. Исходные синтетические fixtures сохранены
для быстрых unit-тестов и старых моковых CLI/UI Сергея; они не выдаются за HyDRA.

## Что проверяем

Публичный вопрос: почему команда, полученная через SQL по итогам сезона,
приостановила деятельность после сезона 1918–19. Исходный SQL из HyDRA:

```sql
SELECT T2.name FROM TeamsSC AS T1
INNER JOIN Teams AS T2 ON T1.tmID = T2.tmID AND T1.year = T2.year
WHERE T1.year = '1917' AND T1.W > T1.L
```

На исходной BIRD-базе hockey он возвращает columns=["name"], rows=[["Toronto Arenas"]].
Запрос сохраняется без исправлений. Выполняется настоящий SQL-тул харнесса через
Python SQLClient → Go HTTP API → read-only SQLite. Затем поисковый запрос строится
из публичного вопроса и реально полученных SQL-значений. Gold search_answer и
подсказки в запрос или поисковый индекс не передаются.

Режим называется `gold_sql_tool_replay_without_agent`: SQL задан тестом из эталона,
а не сгенерирован моделью. Успех означает работоспособность SQL/search-инструментов,
не самостоятельное решение задачи агентом и не качество обучения.

## Данные

Задача: Snowflake/HyDRA-Bench, train_a2s.json, ревизия
`176151eea2e171b674af961fa5d1b2b33eaa6e76`. SQL: BIRD hockey, проверенная по SHA-256
копия из IBM VAKRA, 6,9 МБ. Корпус: CoRAG-конвертация KILT/Wikipedia 2019,
ревизия `bf95d9b4b19c68420395efad7498d0ef5052ab4b`.

В самом HyDRA опубликованы вопросы, SQL и эталоны, но не весь корпус и SQL-файлы.
Выбрана Parquet-группа 435 из `train-00015-of-00037.parquet`, содержащая страницу
Toronto Arenas, Wikipedia id 237029. Из 1000 исходных записей одна пустая исключена.
Остались 999 настоящих фрагментов, из них 16 относятся к нужной странице.

Это специально подобранный диагностический срез с гарантированным наличием страницы,
не репрезентативная выборка полного KILT. Ручной hit@10 по странице не равен
официальному Recall@10: qrels для этой HyDRA-записи не опубликованы. Наличие фрагмента
нужной страницы также не доказывает правильность финального ответа. В просмотренных
KILT-фрагментах описаны низкая посещаемость, уход игроков и проблемы с контрактами;
утверждения search_answer HyDRA о legal bills и продаже игроков отдельно не подтверждены.
Смысловую accuracy ответа этот replay не вычисляет.

`examples/fixtures/hydra/task.json` содержит только публичную AgentTask.
`reference.json` — отдельный вход проверки; `corpus.jsonl` — только документы.
`provenance.json` фиксирует источники, хеши и соответствие passage id → Wikipedia id.
Лицензии и атрибуция — в [ATTRIBUTION.md](../examples/fixtures/hydra/ATTRIBUTION.md).
База, веса, индексы и результаты исключены из Git.

## Запуск

Из корня репозитория, Go 1.25+, Python 3.11+:

```bash
python -m pip install -e '.[dev,hydra]'
python examples/prepare_hydra.py --with-vectors
go -C services/search build -o ../../build/search-service ./cmd/search
./build/search-service build
./build/search-service serve -sql-snapshot data/hydra/hockey.sqlite -db-id hockey
```

В другом терминале:

```bash
python examples/run_hydra.py --with-vectors
```

Скрипт проверяет SQL, поиск и соответствие чтения исходным фрагментам; сохраняет
`runs/hydra/train_a2s_4.json`, FAISS-индекс и манифест. В стандартном проверенном
запуске SQL совпал, BM25/FAISS/RRF дали manual_reference_hit_at_10=true.
По одной задаче нельзя выбирать победителя или объявлять превосходство метода.

Без векторов достаточно основной установки проекта и команд без `--with-vectors`.
Поиск тогда использует Go BM25. Для сверки корпуса с опубликованным Parquet:

```bash
python examples/prepare_hydra.py --verify-corpus-source
```

Команда читает только одну известную группу через HTTP Range и проверяет SHA-256,
не скачивает полный корпус. При первом исследовании Hugging Face search/filter
возвращали HTTP 500; Data Studio оставался в загрузке. Точные координаты группы
позволяют воспроизвести срез без серверного поиска HF.

## BM25, FAISS и их объединение

BM25 использует существующий Go FTS5-бэкенд. Диагностический dense-бейзлайн находится
в `search/semantic.py`, потому что FAISS и ONNX имеют готовые Python-пакеты.
Go-сервис и контракт SearchBackend не переписаны на Python.

Энкодер — фиксированный all-MiniLM-L6-v2, опубликованный ONNX int8 весом 23 МБ,
CPUExecutionProvider, без GPU и платных API. Это англоязычный пилот, не выбранная
модель для будущего RU/EN-продукта. Окна по 224 токена со stride=192,
attention-mask mean pooling и L2-нормализация. Векторы размерности 384 ищутся
через точный FAISS IndexFlatIP; score соответствует cosine для нормализованных векторов.
Манифест записывает хеши весов/токенизатора, параметры и версии библиотек.

Для малого корпуса просматриваются все векторы и затем выбираются уникальные
doc_id по лучшему фрагменту. Это исключает потерю top-k документов при дедупликации.
Гибрид — reciprocal rank fusion двух top-10 выдач с фиксированным k=60,
без подбора весов по эталону. Dense-вариант пока экспериментальный: он сравнивается
с сервисом в replay-скрипте, а не подключён как новый режим HTTP-сервиса.

## SQL API

Опциональные флаги serve: `-sql-snapshot PATH -db-id ID`.
GET `/v1/sql/schema` возвращает db_id, db_revision=SHA-256 файла и публичную схему.
POST `/v1/sql` принимает query, db_id, db_revision; возвращает columns, rows,
truncated и те же id/ревизию. SQLClient реализует существующий SqlBackend.
Дублирующиеся имена колонок сохраняются списком и не затирают значения.

Файл открывается mode=ro, query_only=1, trusted_schema=0. Разрешён один SELECT/WITH;
служебные операторы, ATTACH/DETACH, PRAGMA и функции загрузки расширений/файлов
отклоняются. Это ограниченный SQLite-интерфейс для доверенного снимка, не поддержка
всех диалектов и не полноценный SQL-парсер. Ограничения: 100 строк, 100 колонок,
256 КиБ содержимого результата, 1 МБ SQLite length; deadline включает очередь.
Ошибки запроса дают sql_query_error/HTTP 400 → SqlQueryError модели;
инфраструктурные ошибки не превращаются в пустой ответ или нулевую оценку.

## Аудит первой записи и проверки

Первоначально просмотренная `train_a2s_0` не использована как положительный пример:
её SQL возвращает две колонки Government со значениями
`special administrative area in China` и `Communist state`, а опубликованный
sql_output хранит только одно значение под одинаковым ключом. Вопрос просит длину
границы, но исходный SELECT длину не возвращает. Это расхождения исходной записи;
их нельзя исправлять в нашем SQL-туле или выдавать за его ошибку.

```bash
go -C services/search test -race ./...
go -C services/search vet ./...
python -m pytest -q
```

Unit-тесты не скачивают данные/модели. Реальный SQL integration использует подготовленный
data/hydra/hockey.sqlite; без него явно пропускается с инструкцией подготовки.
Дальше нужны пилот из нескольких независимых задач, согласованные qrels/оценщик,
реальный сценарий агента и отдельный выбор многоязычного энкодера.
