# Решение по проекту

Разрабатываем собственный GEPA-like оптимизатор для собственного Text-to-SQL + RAG-харнесса. Между пользовательскими запросами он анализирует завершённые траектории и отбирает версии инструкций. Сначала меняются промпты, затем добавляется создание и редактирование текстовых skills. Веса модели фиксированы.

Первый результат команды — рабочий статический харнесс и воспроизводимые исходные замеры. Затем сравниваем static, Hermes-like memory-only и prompt-evolution на одном потоке. Качество определяет независимая оценка первой попытки на следующих запросах.

В основном эксперименте адаптации доступны запрос, ответ, публичные вызовы и результаты инструментов, ошибки и суждения внутреннего критика. Эталонный SQL, ответы, метки документов, benchmark reward и оценки исследователей доступны только независимому оценщику. Исправления с правильным ответом допустимы в отдельном явно обозначенном эксперименте.

Сергей ведёт харнесс, оптимизатор и сравнение с памятью. Дима отвечает за источники и воспроизводимый replay, Коля за runner, версии и расходы, Вова за задачи и независимый eval. Целевой runtime запускается в окружении без Verifiers. Первый кандидат для проверки — OpenAI Agents SDK. Задержку измеряем как эксплуатационную характеристику. Приоритет статьи — качество следующих ответов, надёжность отбора и полная стоимость адаптации.

[Архитектура](docs/RUNTIME_OPTIMIZER.md) · [Этапы](docs/ROADMAP.md) · [Статья](docs/PAPER_PLAN.md).



Сохранять незакоммиченные изменения команды. Документация и отчёты — по-русски, кодовые идентификаторы — по-английски. Ключи не хранить в отслеживаемых файлах. Платные API/cloud/GPU-прогоны требуют отдельного разрешённого бюджета; тяжёлые вычисления и загрузку весов на Mac не запускать.
