# Правила работы с репозиторием

Работаем над открытой RL-средой для поисковых агентов. Основной пример — обучение собственного агента и сравнение его качества до и после обучения на отложенных задачах. Распределение ответственности — в [TASKS.md](docs/TASKS.md), план папок — в [STRUCTURE.md](docs/STRUCTURE.md).

## Задача перед разработкой

Для задачи создаём issue по шаблону: цель, исполнитель, ожидаемый результат и способ проверки. Один человек ведёт задачу до готового результата; остальные могут помогать. Крупную работу разбиваем на части, которые можно отдельно проверить и влить.

Перед изменением общего интерфейса записываем пример входа и выхода в [CONTRACTS.md](docs/CONTRACTS.md) и обсуждаем его с владельцами обоих компонентов. Собственные детали реализации внутри модуля исполнитель выбирает самостоятельно.

## Ветки и коммиты

`main` содержит согласованное состояние проекта. Изменения вносим через короткие рабочие ветки и pull request. Прямой push и force push в `main` не используем.

Имена веток: `<тип>/<краткое-описание>` на английском. Примеры: `feat/search-api`, `feat/benchmark-runner`, `fix/duplicate-document-ids`, `docs/data-format`. Отдельные постоянные ветки на каждого участника не нужны.

После первого опубликованного `main` обычное начало задачи:

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/search-api
```

Коммиты называем коротко, в повелительной форме: `Add search result schema`, `Fix duplicate document scoring`. Коммит должен содержать связанную правку; случайное форматирование соседних файлов выносим отдельно. Секреты, большие данные и результаты прогонов в коммиты не добавляем.

## Pull request и ревью

Один PR решает одну понятную задачу. Незавершённую работу можно открыть как draft, чтобы показать интерфейс и получить обратную связь.

В описании указываем:

- какую задачу решает изменение и ссылку на issue;
- что изменилось, включая общий формат данных или конфигурацию;
- как проверяли: команды, результат и значимые ограничения;
- для экспериментальной правки — конфиг, id MLflow-прогона и сравнение метрик.

Перед слиянием нужен хотя бы один ревьюер кроме автора, знакомый с изменяемым участком. Сергей ревьюит харнесс, модели и обучение; Дима — хранение и поиск; Коля — инфраструктуру прогонов; Вова — задачи, метрики и джаджей. Для первых PR Коли по технической части ревьюером выступает Сергей или Дима. Изменение на границе компонентов смотрит и владелец затронутого соседнего компонента.

Автор устраняет замечания и конфликты, затем PR сливается через squash с понятным итоговым сообщением. После слияния рабочую ветку удаляем. Эти правила — договорённость команды; настройки защиты ветки на GitHub должны быть настроены отдельно.

## Границы модулей

Агент обращается к поиску через согласованный интерфейс. Инфраструктура прогонов вызывает харнесс, затем оценщики бенчмарка. Оценщики могут считать метрики по уже сохранённым результатам без повторного запуска агента.

Общие типы и примеры данных находятся в `contracts/` будущего пакета. В код одного компонента не копируем бизнес-логику другого. Модули не импортируют CLI и скрипты запуска. Конкретная база данных и провайдер модели выбираются конфигурацией, а не зашиваются в общий цикл агента.

## Код и документация

Код и идентификаторы — по-английски; документация и отчёты — по-русски. Для Python используем четыре пробела, `snake_case` для функций и модулей, `PascalCase` для классов. Форматтер и линтер пока не выбраны.

Меняется интерфейс — обновляем его описание и примеры в том же PR. Добавляется команда — документируем установку, аргументы и ожидаемый результат. В README не публикуем команды, которые ещё не реализованы. Ссылки в общих документах должны работать из отдельного клона этого репозитория.

## Проверки

Сейчас исполняемого пакета и тестового окружения нет. Для правок документации проверяем ссылки, примеры и `git diff --check`.

При появлении Python-кода используем pytest. Быстрые проверки должны запускаться без ключей, загрузки весов и GPU: расчёт награды, повторные id, ограничения эпизода, ошибки действий, сохранение и возобновление. Для интеграционных проверок используем небольшой синтетический пример из `examples/fixtures/`. Внешние API и GPU запускаются отдельно с явной конфигурацией; схема маркировки и команды добавляются вместе с тестовым окружением.

## Данные и эксперименты

Train/dev/test разделяем до создания производных формулировок и траекторий. Переводы, перефразы и префиксы одного вопроса остаются в одной группе. Эталоны доступны оценщику, но не входят в наблюдение агента. Внешние оценочные наборы не используем для обучения и выбора чекпоинта.

Для набора фиксируем источник, лицензию, ревизию и контрольные суммы. Для прогона сохраняем commit SHA, изменения рабочей копии при их наличии, конфиг, seed, версии моделей и данных, промпты, лимиты, траектории, метрики и затраты. Трекинг ведём в MLflow. Джаджи имеют собственные версии, промпты и параметры; их ошибки проверяет Вова на ручной выборке.

Большие корпуса, индексы, веса и результаты храним вне Git. В репозиторий входят конфиги, манифесты и небольшой синтетический пример, достаточный для проверки кода.

## Конфигурация и расходы

Ключи передаём через переменные окружения или локальный `.env`. В отслеживаемых примерах оставляем только названия переменных и пустые значения. Конфиги не содержат ключей и абсолютных путей конкретного разработчика.

Платные API и GPU-прогоны запускаем после явного разрешения Сергея на конкретный бюджет. Пакетный запуск должен иметь лимит, учёт расходов и возможность продолжения. Долгие вычисления и загрузку весов на Mac не начинаем. Результаты удалённого обучения сохраняем вместе с логами и проверяем после скачивания.
